# 6.0.0 宿主—模块统一契约设计稿

- 状态：**已批准**（2026-09-30，用户「全部拍板」，第八节按建议执行）；第一段 5.9.0 已完成（DEC-070；与本稿的偏离：数据目录在包槽位之外、目录行给 RequiresConfirmation 而非文案、C2 另有 Publish、来源盖章推迟到 6.0.0）
- 日期：2026-09-30；基于宿主 5.8.0（`34f4fc9`）与 9 个模块仓当日 main 的只读摸底
- 来源：用户指出「动宿主的代价越来越大，改宿主要关心每一个模块，而不是宿主与模块的统一契约」，要求以指令总线为统一契约
- 范围：宿主对模块暴露的全部面（编译期程序集、运行期上下文、总线载荷、文件与进程约定、测试装载）。
  **不改**模块内部实现、Aurora 的界面描述协议（`ui.*` 注解词汇）、开发管线阶段。

## 一、目标与判据

**目标**：宿主只对一份「统一契约」负责。模块增减、模块内部改动不改宿主；宿主内部重构不影响任何模块。

判据都要能机械检查（见第七节）：

| 编号 | 判据 |
| --- | --- |
| G1 | 模块只引用契约程序集 `HistoryVulcan.Core`，不引用 `Services` / `ServiceHost` / 宿主测试程序集 |
| G2 | 宿主源码不出现任何具体模块名或模块指令域（示例文字除外） |
| G3 | 模块↔宿主、模块↔模块的交互只走两条路：总线指令（含事件），或 `IModuleContext` 上的成员。不经文件路径、进程名、进程参数、CLR 类型强转 |
| G4 | 总线载荷的契约是**写明的 JSON 形状**，不是宿主某个 C# 类 |
| G5 | 契约程序集的公开面有白名单，超出即门禁失败 |

## 二、现状摸底

### 2.1 已经统一的部分

- 身份与装载：`module.manifest.json`（schemaVersion/type/name/version/artifact/docs/mcpExposure/ui/pinned/dependsOn）
  加 `ModuleInfoBase` 全名鸭子类型。
- 上下文 `IModuleContext` 只有 4 项：`Bus`、`Log`、`RegisterCommands`、`RegisterFrontend`。
- 就绪钩子 `<域>.host.ready` 走总线指令——这是统一契约的正面样板：宿主只认命名规则，不认模块。
- 发布描述：5.8.0 起由模块仓 `project.manifest.json` 的 `publish` 节自带（DEC-069）。
- **9 个模块里 7 个只用两件事**：`Registry.Register` 与 `Bus.ExecuteAsync`（Janus 另有一次 `Bus.RequestConfirmation`）。

| 模块 | 用到的总线/注册表成员 | 引用的宿主程序集 |
| --- | --- | --- |
| Diana | Register×21、ExecuteAsync×3 | Core |
| Janus | Register×53、ExecuteAsync×41、RequestConfirmation×1 | Core、**Services**（仅 ModuleSmoke） |
| Mercury | Register×1、ExecuteAsync×7 | Core、**Services**；另对宿主测试程序集开 InternalsVisibleTo |
| Minerva | Register×19、ExecuteAsync×6 | Core、**Services**（仅 Smoke） |
| Juno / Apollo / Strenua | 只有 Register（Strenua 另 ExecuteAsync×1） | Core |
| **Aurora** | ExecuteAsync×43、Bus.Registry×18、Registry.All×8、RemoteExecutor×7、TryGet/GetSource/GetDomain×5、GetCommandClass×4、Changed×4、Validate×3、InvokeAsync×2、Suggest、Executed | Core、**Services（产品代码）** |
| **Portunus** | Bus.Registry×7、Register×6、ExecuteAsync×3、Registry.All×2、Confirmation×2、TryGet | Core |

### 2.2 特例一：总线交出去的是具体类

`IModuleContext.Bus` 的类型是 `CommandBus`（具体类），`RegisterCommands` 给的是 `CommandRegistry`（具体类）。
于是 Core 的 **213 条** Shipped 公开面全部成了事实契约：`Registry`、`RemoteExecutor`、`ShouldUseRemoteCommand`、
`UiContext`、`Confirmation`、`Validate`、`InvokeAsync`、`Executed`、`FormatUsage`、`Registry.Changed/Suggest/GetSource/Unregister`……
其中不少 5.4.0 已在宿主总线上「封口只读」，但签名仍在契约里，宿主改它们仍要看 Aurora、Portunus 的脸色。

更深一层：**Aurora 自己 new 了第二套 `CommandBus` + `CommandRegistry`**（独立进程时代的遗留），
把 `RemoteExecutor` 指向宿主总线，再把自己的指令逐字段抄成代理登记进宿主表（`AuroraShellHost.PublishShellCommands / Marshalled`）。
这让 `CommandBus` 从「宿主给模块的通道」变成了「Aurora 复用的类库」，宿主改总线实现就等于改 Aurora。
而宿主总线自 5.4 起已经会把 `RequiresUiThread` 指令编组到前端的 `UiContext`，第二套总线已无必要。

### 2.3 特例二：载荷用宿主实现程序集的 C# 类型

`HistoryVulcan.Services` 公开 **143 条**：`ModuleHost`、`RuntimeModuleDiscoverySource`、`ModuleMeta`、`CommandCatalogRow/Detail`、
`CommandParameterInfo`、`CommandDomainInfo`、`ModuleDiscovery*`。消费方：

- Aurora 产品代码：把 `vulcan.module.list` 的 Data 用 `CommandResultData.TryRead<IReadOnlyList<ModuleMeta>>` 强转；
  指令目录、指令详情页用 `CommandCatalogRow/Detail/CommandParameterInfo`。**只在同进程成立**，且把宿主内部 DTO 焊进了 Aurora 二进制。
- Janus `ModuleSmoke`、Minerva `Smoke`、模板 `0000-002` 的装载测试：直接 `new ModuleHost(...)`。5.3.0、5.4.0 两次「宿主一动模块测试就编不过」都在这里。
- Mercury：产品代码 `using HistoryVulcan.Services.Commands` 但实际未用到类型；csproj 还对 `HistoryVulcan.Tests` 开了 InternalsVisibleTo（方向反了）。

### 2.4 特例三：总线之外的暗约定

| 约定 | 现状 | 谁受影响 |
| --- | --- | --- |
| 模块数据目录 | 宿主 5.0 起不给（模块API「数据根按约定自行拼接」），但宿主内部又有常量 `MutableDataDirectoryName = "data"`，装包时保留 `槽/data`。模块各写各的，至少 5 种布局：Janus、Apollo `Modules/<名>/data`；Portunus 用宿主公共的 `state/`、`service/logs/`；Mercury `HistoryVulcan/<名>`；Minerva 自配；Aurora 自有根 | 宿主一调整运行区布局，要逐个模块核对 |
| 运行模式 | 宿主不告诉模块当前是正式服务、离线 CLI 还是测试装载 | Portunus 只好读进程参数里有没有 `--cli`（`HostLaneClaim`） |
| 宿主位置与设置 | 没有查询入口 | Mercury 按进程名找 `HistoryVulcan.exe`、写死 `2026-023-HistoryVulcan/z-Publish`；Diana 按路径探宿主 z-Publish；Mercury 曾直接读宿主 settings.json |
| 模块间文件通道 | `endpoint.json` 由 Portunus 写、Diana 读，再经 HTTP 调 MCP | 模块↔模块绕开总线 |
| 调用来源 | 模块经总线调用时自己填 source；Diana 填自己的指令名 | 宿主 `IsLocalModuleMutationSource` 因此写死信任 `diana.` 前缀 |

### 2.5 宿主源码里按模块写的特例

- `ServiceComposer.IsLocalModuleMutationSource`：`source.StartsWith("diana.")` 视为本机可信。
- `CommandCatalogCommands`（`vulcan.cli.list/show`）：`portunus.` 开头判为 runtime-only。CLI 白名单里已无 `portunus.*`，是死代码。
- `BuiltinCommandDefinitions`：宿主声明 `vulcan.command.help`、`vulcan.app.get/set`，由前端实现——这是「前端角色」契约，但目前没写成角色契约。

**结论**：统一契约（总线）已经存在，7 个模块也只用它。代价来自三类特例：前端/传输角色直接用总线内部，
载荷用宿主实现类型，数据目录/运行模式/宿主位置没有契约只好各自猜。

## 三、统一契约（提案）

一句话：**宿主给模块的只有「一条总线 + 一个上下文」；总线 = 指令 + 事件；载荷 = 写明的 JSON 形状。**

### C1 身份与装载（不变）

`module.manifest.json` 与 `ModuleInfoBase` 维持现状；`dependsOn`、`<域>.host.ready` 维持现状。发布描述维持 5.8.0 的 `publish` 节。

### C2 上下文 `IModuleContext`

```csharp
public interface IModuleContext
{
    ICommandBus Bus { get; }                                  // 窄接口，见 C3
    IModuleLog Log { get; }                                   // 只写：Log(level, category, message)
    void RegisterCommands(Action<ICommandRegistrar> configure); // 只有 Register(descriptor)
    IDisposable Subscribe(string topic, Action<BusEvent> handler); // 见 C4
    IModuleEnvironment Environment { get; }                   // 见 C6
    IDisposable RegisterFrontend(IFrontend frontend);          // 前端角色，见 C5
}
```

- 宿主经 `Bus` 执行模块调用时**由宿主盖来源章** `module:<模块名>`，模块不再自填 source。
  本机可信判定改为「`module:` 前缀一律视为本机」，删除 `diana.` 特例。
- 模块只能加指令，不能枚举、删除、改写宿主表；卸载时随模块整体回收（现状如此，只是把能力收窄到接口上）。

### C3 窄总线 `ICommandBus`

```csharp
public interface ICommandBus
{
    Task<CommandResult> ExecuteAsync(string text, string source = "", CancellationToken cancellation = default);
    bool RequestConfirmation(string prompt);
}
```

目录、校验、补全、帮助全部改成**只读总线指令**（MCP 隐藏与否按现行描述符规则）：

| 需求（现由谁直接调内部） | 契约指令 | Data 形状 |
| --- | --- | --- |
| 指令目录（Aurora 目录页、Portunus 工具表） | `vulcan.command.list`（已有，补全字段） | `CommandInfo[]`，见 C7 |
| 单条详情（Aurora 详情、Portunus 确认提示） | `vulcan.command.show`（已有） | `CommandInfo` |
| 输入校验（Aurora 输入框） | `vulcan.command.validate text=`（新） | `{ ok, usage?, error? }` |
| 未知指令建议 | `vulcan.command.suggest name=`（新） | `string[]` |
| 模块列表（Aurora 模块页） | `vulcan.module.list`（已有） | `ModuleInfo[]`，见 C7 |
| 目录版本（廉价判断要不要重拉） | `vulcan.command.revision`（新） | `{ revision }` |

### C4 总线事件

现在靠 C# 事件订阅的三件事（`Registry.Changed`、`Bus.Executed`、`IShellLog.EntryAdded`）改为总线上的具名主题：

| 主题 | 发布方 | 载荷（JSON） | 现消费方 |
| --- | --- | --- | --- |
| `vulcan.catalog.changed` | 宿主 | `{ revision, added[], removed[] }` | Aurora 目录、Portunus 工具表 |
| `vulcan.module.changed` | 宿主 | `{ name, version, attached, reason }` | Aurora 模块页、Diana 观察 |
| `vulcan.command.executed` | 宿主 | `{ name, source, success, summary }`（不含 Data 全文） | Aurora 控制台 |
| `vulcan.log.entry` | 宿主 | `{ time, level, category, message }` | Aurora 控制台 |
| `<域>.*` | 模块自己 | 模块自定 | 其他模块 |

- 事件是**通知**，不是 RPC：订阅方要细节就再调只读指令。处理器在线程池上异步投递，抛异常只记日志，不影响发布方。
- 模块自己的主题必须以自己的指令域开头（与指令同一套命名规则），宿主只校验前缀，不认识内容。
- 替代「模块间写文件互读」：Portunus 端口变化发 `portunus.endpoint.changed`，Diana 订阅；或 Diana 直接调 `portunus.endpoint.show`。

### C5 前端角色（保留，写成角色契约）

- `RegisterFrontend(IFrontend)` 与 `IFrontend { UiContext, Confirm, ExecuteAsync }` 不变；同一宿主只允许一个前端。
- 前端的指令直接经 `RegisterCommands` 登记，标 `RequiresUiThread = true`，由宿主编组到 `IFrontend.UiContext`。
  **Aurora 不再自建第二套总线与注册表**，也不再逐字段抄代理描述符。
- 宿主声明、前端实现的共享指令（`vulcan.command.help`、`vulcan.app.get/set`）写进角色契约：前端必须实现，无前端时宿主答「无前端」。
  是否改归 `aurora.*` 域见第八节待定项。

### C6 运行环境 `IModuleEnvironment`

```csharp
public interface IModuleEnvironment
{
    string DataDirectory { get; }    // 槽/data：装包、热重载保留；卸载时按 vulcan.module.uninstall 的 purge 决定
    HostRunMode RunMode { get; }     // Service / OfflineCli / Probe（测试装载）
    string HostVersion { get; }
}
```

另加只读指令 `vulcan.host.info`：`{ version, runMode, libraryRoot, worktreeRoot, modulesRoot, hostExecutable }`，
供 Mercury 找宿主可执行文件、Diana 找宿主快照，替代按进程名/固定路径猜。

`DataDirectory` 的落点就是宿主现有的 `槽/data`（`RuntimeModulePackageStore.PreserveMutableData` 已在保留它），
只是从「内部常量」升格为「契约」。已有数据的模块迁移一次（第六节）。

### C7 载荷形状（写进模块API，宿主改内部类不影响）

```jsonc
// CommandInfo
{ "name": "janus.proj.list", "domain": "janus", "commandClass": "proj", "method": "list",
  "summary": "…", "example": "…", "source": "module:HistoryJanus",
  "readonly": true, "level": "run|ask", "confirmPrompt": null, "hiddenReason": null,
  "requiresUiThread": false, "allowUnspecifiedParameters": false,
  "parameters": [ { "name": "…", "type": "string|int|double|bool", "required": true,
                    "default": null, "position": 0, "allowedValues": [], "description": "…" } ],
  "annotations": { "ui.page": "…" } }

// ModuleInfo
{ "name": "HistoryJanus", "version": "5.12.2", "description": "…", "attached": true,
  "commandCount": 53, "ui": true, "pinned": false, "attachFailures": [], "dataDirectory": "…" }
```

- 形状只增不减；删字段或改语义走主版本。消费方按名取字段、忽略未知字段。
- 宿主内部可以继续用 `ModuleMeta`、`CommandCatalogRow` 等类，但它们退回 `internal`，Data 输出前序列化成上述形状。
- Core 提供极薄的只读辅助（例如 `CommandInfo` 记录类型与 `CommandResultData.Read<T>` 的 JSON 反序列化），**形状以 JSON 为准**，辅助类型只是便利。

### C8 测试装载：用宿主 CLI，不用宿主类

删除 Services 的公开 `ModuleHost` 测试装载器。模块 Smoke 改为调宿主已发布的 CLI：

```text
HistoryVulcan.Cli.exe --probe <包目录> --cli "<指令>" --format json
```

`--probe` 起一个只装这一个包（加其 dependsOn 里已安装的包）的离线组合，`RunMode = Probe`，
返回信封里带附着结果（attached、attachFailures、commandCount）与指令结果。模板 `0000-002` 的装载冒烟同样改用它。

## 六、迁移顺序

分三段，每段结束时全体模块都能正常装载，不存在「一刀切」的窗口。

**第一段 5.9.0（纯增量，不破坏任何模块）**

1. 新增：`ICommandBus`/`ICommandRegistrar`/`IModuleLog`/`IModuleEnvironment`/`Subscribe`（接口成员带默认实现，照顾 Diana、Minerva 自写的 `IModuleContext` 替身）；
   `CommandBus`、`CommandRegistry` 实现对应窄接口；`IModuleContext.Bus` 暂仍返回具体类。
2. 新增指令：`vulcan.command.validate/suggest/revision`、`vulcan.host.info`；`vulcan.command.list/show`、`vulcan.module.list` 的 Data 输出 C7 形状（旧 CLR 类型同时保留）。
3. 新增事件主题 C4；`--probe` CLI。
4. 宿主盖来源章 `module:<名>`，`IsLocalModuleMutationSource` 同时接受旧 `diana.`；删 `portunus.` 死代码。
5. 数据目录：`Environment.DataDirectory` 指向 `槽/data`。

**第二段：模块逐个迁移（各走 dev 管线，互不依赖）**

顺序建议：模板 → Apollo/Juno/Strenua → Janus/Minerva/Mercury/Diana → Portunus → Aurora。
每个模块迁完即满足 G1/G3；有旧数据的模块在 `host.ready` 里做一次性搬迁（旧目录保留，不删）。

**第三段 6.0.0（主版本，收口）**

1. `IModuleContext.Bus` 类型改为 `ICommandBus`，`RegisterCommands` 改为 `ICommandRegistrar`；`CommandBus`/`CommandRegistry` 与 Services 全部公开类型退回 internal。
2. 删 `diana.` 兼容、删旧 CLR 载荷。
3. 冻结线推进到 `v6.0.0`，按第七节开门禁。

## 七、门禁（机械守住）

| 判据 | 守在哪里 |
| --- | --- |
| G1 | 模板合同脚本：csproj 只许引用 `HistoryVulcan.Core`；宿主 `release.cycle` 扫项目库自带 publish 的模块 csproj，越界给警告（不拦宿主发版） |
| G2 | 宿主测试：把 5.8.0 的「管线源码不出现模块名」扩到全部宿主源码（示例字符串白名单） |
| G3 | 宿主测试：宿主源码不出现 `StartsWith("<某模块域>.")` 这类判断；模板合同脚本禁止拼 `%AppData%\HistoryVulcan` |
| G4 | 宿主测试：C7 形状快照测试，字段只增不减 |
| G5 | Core PublicAPI 白名单测试：出现白名单外类型即失败 |

## 八、拍板结果（2026-09-30）

用户确认全部按本稿建议执行：1 卸载默认保留 `槽/data`，`purge=true` 才删；2 通用具名主题；3 `vulcan.app.*`、`vulcan.command.help` 留在 `vulcan.*`；4 推翻 5.0 决定，宿主给数据目录；5 Diana HTTP 中继保留，只是不再读 `endpoint.json`；6 Aurora 单独迁移，不等功能版本。

另：实施时确认 Aurora 读 Data 只接受「同一 CLR 类型」或 `JsonElement`，因此 5.9.0 期间 `vulcan.command.list/show`、`vulcan.module.list` 的 Data 保持原类型、只追加字段，C7 形状以这些类型的**序列化结果**为准（字段名沿用现有 `commandName` 等），6.0 再把类型收回 internal。

### 原待拍板项

1. **数据目录卸载语义**：`vulcan.module.uninstall` 默认保留 `槽/data`，`purge=true` 才删？还是默认删？（建议默认保留）
2. **事件通道形态**：通用具名主题（本稿方案）还是每类事件一个强类型接口？通用主题让模块也能发事件、宿主不必随新事件改契约；代价是载荷只靠 JSON 约定。（建议通用）
3. **前端共享指令归属**：`vulcan.app.get/set`、`vulcan.command.help` 留在 `vulcan.*` 作为前端角色契约，还是改归 `aurora.*`？（建议留，改名会打断 MCP 客户端的既有调用）
4. **是否推翻 5.0「不给模块数据根」的决定**：本稿认为当年的顾虑（宿主替模块管状态）不成立——宿主只给路径、不管内容，而现状是 5 种各猜各的。需你确认。
5. **Diana 经 HTTP 调 MCP 的中继**：属于模块↔模块，按 G3 应改走总线；但它的用途是给「接不上 MCP 的 AI」兜底，可能需要保留 HTTP 路径。本稿只要求它不再读 `endpoint.json`。
6. **节奏**：第一段 5.9.0 可以马上做；第二段 Aurora 的迁移量最大，是否和 Aurora 下一个功能版本合并？
