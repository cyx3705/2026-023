# 宿主轻量化报告

> 版本基准：HistoryVulcan 4.8.0（暴露级收敛完成之后）
> 性质：**测量与方案，不含执行**

---

## 0. 一句话结论

宿主还有 **10 575 行**。按"只剩模块注册器 + 指令总线 + 通用暴露面"这个目标衡量，
其中约 **3 400 行不属于宿主**，另有约 **1 900 行属于宿主但可以显著变薄**。

但方向要先纠正一处：你说的"演进层和 Core 可以合并了"——**合并本身是对的，
却不是减量的主要来源**。测量显示演进层 699 行里，宿主自己消费的只有约 240 行；
Core 的 2 623 行里，宿主自己消费的约 1 900 行。真正的减量来自
**把"宿主自己不消费"的契约迁出去**，而不是把两层并成一层。

先合并再迁出，会把一堆本该走的东西焊死在冻结契约里。**顺序应当反过来。**

## 2. 演进层：不是合并，是清空

逐个类型扫了全体系的消费方（排除定义处本身）：

| 类型 | 消费方 | 处置 |
|---|---|---|
| `ConsoleCompletionTypes` | **零** | **删除** |
| `CommandManualGenerator` | 仅宿主 | 并入 Core，跟着总线走 |
| `CommandSchemaExporter` | 宿主 / Minerva / Portunus | 并入 Core（见下） |
| `ICommandCatalogSession` | Mercury / Aurora | **迁出**——宿主零消费 |
| `IShellCommandWorkbenchHost` | Mercury / Aurora / 宿主 | **迁出**（宿主那 1 处是转交） |
| `PanelDefinition` | 仅 Aurora | **迁出 Aurora** |
| `CommandClassLabels` | 宿主 / Aurora | 拆：标签给 Aurora，判定留 Core |
| `DomainFocus` | Mercury / Aurora / 宿主 | **迁出** |

**结论：演进层 8 个类型里，5 个是模块与模块之间的约定，只是暂存在宿主里。**
它们让宿主看起来"支持界面/目录/面板"，实际上宿主一行都不执行。

`CommandSchemaExporter` 是唯一真正该留下的：它把注册表投影成 MCP schema，
是**通用暴露面**的一部分——正是你说的"消费挂载暴露面"里那个"面"。
`CommandManualGenerator` 同理（`--export-command-manual` 是宿主自己的出口）。

> 迁完之后 `HistoryVulcan.Extensibility` 只剩这两个投影器，约 240 行，
> 那时并入 `Core/Commands/` 才是水到渠成，而不是把 460 行外来契约一起焊进冻结层。

## 3. Core 上的迁移遗留

### 3.1 `Clients/`（66 行）—— 只有 Portunus 用

`ClientSession` / `ClientKind` 是 Web 网关的会话模型。网关已整体迁往 Portunus，
这两个类型留在 Core 的唯一理由是"它属于冻结的公开面"——那是循环论证。

`WebGateway.Authenticate` 的注释自己写着：删除局域网面之后不再有"部分授权"的
中间态，`ClientSession.Scopes` 仍填齐只是因为它属于冻结的 Core 公开面。
**一个字段因为冻结而保留，又因为保留而继续冻结。**

→ **整目录迁往 Portunus。**

### 3.2 `Mcp/`（333 行）—— 一半该走

| 类型 | 消费方 | 处置 |
|---|---|---|
| `McpExposurePolicy` | 宿主 / Portunus | **留**：暴露判定是通用暴露面 |
| `McpConfirmationScope` | Portunus | 留：确认闸口与总线绑死 |
| `GatewayAwareConfirmation` | Aurora / Portunus | 留：同上 |
| `PromptTextIntegrity` | **仅 Portunus** | **迁出** |
| `IMcpAuditLog` | Portunus（Janus 1 处残留） | **迁出**（先清 Janus 残留） |
| `McpSettingKeys` | Portunus | **迁出** |
| `IMcpPromptGovernanceView` | Portunus | 留：总线上挂着 `McpGovernance` 钩子 |

`McpExposurePolicy` 在 4.8.0 之后已经不持有任何指令名清单，只解释描述符声明 +
模块清单档位。这部分**是**通用暴露面，留得住。

其余约 **150 行**是 MCP 协议细节，跟着门一起走。

### 3.3 `Docking/`（174 行）—— 一行都不属于宿主

| 类型 | 消费方 |
|---|---|
| `IDockingService` / `ShellCommandEventArgs` / `IActivatableToolContent` | 仅 Aurora |
| `ToolWindowDescriptor` / `StandardWindowIds` | Janus / Mercury / Minerva / Aurora |

宿主自己零消费。但**不能简单迁进 Aurora**：那会让 Janus、Mercury、Minerva 三个
模块反过来依赖 Aurora，把"界面是可卸载模块"这条前提废掉——Aurora 卸载时那三个
就编译不过了。

→ 它们属于一个**独立的界面契约包**（如 `HistoryAurora.Contracts`，只含接口无实现），
由 Aurora 与消费方共同引用。宿主不参与。

这一项是本报告里唯一需要新建产物的，也是唯一有真实设计分歧的。

### 3.4 `Storage/`（49 行）

`ISettingsService` 宿主自用（模块经 `IModuleContext` 拿到），**留**。
`ILayoutStore` 只有 Aurora 用（宿主 1 处是 `FileLayoutStore` 实现）——
连同 `Services/FileLayoutStore.cs`（64 行）一起随界面契约走。

### 3.5 `Modules/` 与 `Logging/`、`AppIdentity`

`ModuleContracts`（125）+ `ModuleInfoBase`（40）就是**模块注册器的契约本身**，
`IShellLog`（57）是模块拿得到的三样之一，`AppIdentity`（49）决定数据根与端口派生。
**这些是终局形态里该留的东西，不动。**

唯一可疑的是 `ModuleCommandAttribute`：全体系只有宿主 1 处引用。
需要单独确认它是活的反射入口还是遗留——**本报告未核实，列为待查**。

## 4. Core 之外还剩的复杂部分

### 4.1 `Services/Development/`（1 690 行）—— 最大的一块非宿主职责

`ReleaseCommands`（661）+ `WorktreeCommands`（626）+ `PublishPackages`（200）+
`ProjectLibraryRoot`（55）+ `ModulePackageHotReload`（73）。

它从 Diana 搬进宿主，理由写得很清楚且仍然成立：**修模块的时刻正是模块不可用的时刻，
恢复通道不能建在被恢复的东西上面。**

但"恢复通道必须在宿主进程内可达"不等于"恢复通道的全部实现必须住在宿主里"。
真正不能缺的是 `vulcan.module.install/reload/unload` 那几条（已在 `Modules/` 里）。
`worktree.*` 与 `release.*` 是**开发管线**，它们不参与恢复——
`--cli` 名单把两者混在一起，只是因为当初一起搬。

→ **可迁**，但必须先回答一个问题：迁到哪里而不再犯"Diana 坏了就修不了 Diana"的错。
一个候选是让它成为 **pinned 模块**（装进 `AssemblyLoadContext.Default`，
不随热重载卸载），这样既出了宿主，又不依赖任何可卸载模块。

**这是本报告里收益最大、也最需要你拍板的一项。**

### 4.2 `Services/Modules/`（约 2 600 行）—— 本体，但可以变薄

`ModuleHost` 828 + `Descriptors` 445 + `Reload` 347 + `TypeLoading` 132 +
`Packages` 177 = 1 929 行的装载器，这是"模块注册器"本身，该留。

可以变薄的是**发现源**：`ZModuleDiscoverySource`（407）与
`RuntimeModuleDiscoverySource`（209）是两套并行的发现路径，
前者服务开发期的 z 快照扫描，后者服务运行区。
两者都在做"读清单 → 校验 → 产出候选"，差别只在根目录形状与校验强度。
**合并成一个带策略参数的发现源，估计可省 200～250 行。**

`ModuleDirectoryWatcher`（151）+ `ModulePanelSync`（75）需要重新确认必要性：
面板同步是界面概念，随 Docking 契约一起考虑。

### 4.3 `Services/Commands/CommandCatalogCommands.cs`（408 行）

`vulcan.command.*` 是通用暴露面的自省入口（列指令、看详情、看域），
**属于终局形态**。408 行偏厚主要在 `CommandCatalogRow` 那个 17 字段的投影记录——
它同时服务 Web、Mercury 目录页与 MCP 管理页。4.8.0 之后声明位只剩 4 个，
这个记录**可以跟着瘦一圈**（`Dangerous`、`McpState`、`PolicyVisible`、
`HardExclusionReason` 四列现在有重叠）。

### 4.4 `Services/` 根部的基础设施（446 行）

`ShellLog`（186）、`SettingsService`（124）、`AppPaths`（72）、`FileLayoutStore`（64）。
前三个是宿主给模块的三样基础设施，留；第四个随界面契约走。

## 5. 终局形态

```
HistoryVulcan.Core            ~1 900 行   指令总线 + 描述符 + 注册表 + 解析器
                                          模块契约 + 模块基类
                                          日志契约 + 设置契约 + 身份
                                          暴露判定（McpExposurePolicy）
                                          schema / 手册投影（演进层并入）

HistoryVulcan.Services        ~2 900 行   模块装载器（发现 / 装载 / 热重载 / 包事务）
                                          vulcan.command.* 自省
                                          日志 / 设置 / 路径实现

HistoryVulcan.ServiceHost     ~1 200 行   组合根 + 服务循环 + 入口判定
                                          vulcan.module.* / vulcan.svc.* / vulcan.app.*

App                              ~80 行   分派
────────────────────────────────────────
                              ~6 100 行   （今天 10 575）
```

出宿主的去向：

| 去向 | 内容 | 约 |
|---|---|---|
| **HistoryPortunus** | `Clients/`、MCP 协议细节、`PromptTextIntegrity`、`McpSettingKeys`、`IMcpAuditLog` | 220 行 |
| **界面契约包（新建）** | `Docking/`、`ILayoutStore`、`FileLayoutStore`、`PanelDefinition`、`IShellCommandWorkbenchHost`、`ICommandCatalogSession`、`DomainFocus` | 500 行 |
| **pinned 开发管线模块** | `Services/Development/` | 1 690 行 |
| **直接删除** | `ConsoleCompletionTypes`、发现源合并的重复部分 | 280 行 |

减到 **约 6 100 行**，形状正是你要的：
**一个模块注册器、一条指令总线、一个通用暴露面；模块注册进去，或者挂载消费暴露面。**

---

## 6. 建议顺序

1. **删 `ConsoleCompletionTypes`**，核实 `ModuleCommandAttribute` 与 Janus 的
   `IMcpAuditLog` 残留。零风险，先把测量校准。
2. **MCP 协议细节迁 Portunus**。范围清楚，消费方单一，冻结前必须做完。
3. **界面契约包**。需要先定它的归属与命名——这是唯一有真实设计分歧的一步。
4. **发现源合并**。纯实现层，不动契约。
5. **开发管线出宿主**（pinned 模块）。收益最大、风险最高，放最后，
   而且要先验证 pinned 模块在宿主自身升级时的行为。
6. **演进层并入 Core，然后冻结。** 此刻它只剩两个投影器。

> **不要先合并再迁出。** 合并会把 460 行外来契约焊进冻结层，
> 之后每迁出一样都要走一次公开面移除流程，代价是现在的好几倍。

---

## 7. 本报告未核实的事项

- `ModuleCommandAttribute` 是活的反射入口还是遗留。
- Janus 那 1 处 `IMcpAuditLog` 引用是实现还是残留（上一轮已删过一次实现）。
- `ModulePanelSync` 在界面契约迁出后是否还有存在理由。
- pinned 模块承载开发管线时，**宿主自身升级**该走哪条路——
  pinned 装进 `AssemblyLoadContext.Default` 不可卸载，换宿主时它也换不掉。
  这可能是整个方案的真正边界。
