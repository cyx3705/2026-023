# HistoryVulcan 5.2.1

本仓库是 OneHistory HistoryVulcan（原 AppShell，3.2.0 起改名）的独立源码、合同与发布资产真值。
`5.1.2` 是当前宿主冻结基线，冻结标签名为 `v5.1.2`；`v3.0.3` 只保留为 V3 历史冻结标签。
版本线不再与 HistoryJanus 对齐，`0.7.x` 仅保留用于回滚。

当前源码为 `5.2.1`。5.2.1（DEC-059）修按模块卸载漏清待接入条目：
`vulcan.module.install` 在已装载的同名模块上热装时，宿主会把同一个模块接两遍——
第一遍用已卸载 ALC 的旧类型把旧指令面注册回去，第二遍撞重名指令抛异常，
模块最终 `attached=false`、指令数停在旧值，且重装同一个包不能自愈。
「一个模块在快照里留下哪些痕迹」收口到 `Snapshot.ForgetModule` 一处，
三份 Shipped 与三份 Unshipped 一个符号未动。
5.2.0（DEC-058）是重新冻结前的最后一轮内核清理：指令总线由「一行解析五次」
收成一次，敏感值脱敏不再按写死的命令名判断，十个零消费方的公开成员退役，净减 179 行。
`HistoryVulcan.Core` 在 4.0 阶段性解冻完成前端与模块边界收口（DEC-049），
5.0（DEC-052）拆除宿主模块抽象后，宿主于 5.1.2 正式重新冻结（DEC-056）；冻结面只留注册器、
命令总线和开发/发布总线。
5.1.3（DEC-057）修模块接入次序：装载与接入分成两段，接入按 `module.manifest.json` 的
`dependsOn` 排序逐个进行，接一个登记一个；全部接上后置就绪，`vulcan.module.ready` 可查，
声明了 `<域>.host.ready` 的模块会收到通知。修的是「启动有几率少加载几个模块」这一类竞态，
三份 Shipped 一个符号未动，冻结标签仍是 `v5.1.2`。
3.13.0（DEC-045）删除 Web 网关的局域网面：`WebGateway` 退回纯本机 IPC，固定监听 `127.0.0.1`，
只接受同机前端 Shell，其余一律 401。设备鉴权与配对、令牌鉴权、绑定地址、CORS、限流，以及
从未被注册过的 `WebCommands`（`vulcan.web.*` 五条命令）一并移除，共 48 项公开签名退役。
删除依据是这套机制没有任何生产装配点——鉴权入口只在测试里被赋值过，确认档读的是一个没人写入的
`lan.confirm` 键。MCP 网关自身的鉴权与会话限制不受影响。
同版本（DEC-046）给本机 IPC 通道补上一次性凭据：`WebGateway.Start` 换发 `AccessToken`，经
`endpoint.json` 的 `accessToken` 传给前端，`Authenticate` 要求回环 + Shell + 持券三者同时成立。
在此之前，任何本机进程只要伪造一个请求头就能在权威总线上执行任意命令，MCP 的硬排除因此形同虚设。
独立宿主只从 `%AppData%\HistoryVulcan\Modules\<模块名>` 装载完整 manifest 包；项目库和任何
`z-*` 都不再参与运行发现。`vulcan.module.install/remove` 负责原子安装、移除和失败回滚。
3.11.3 取消模块的文档页注册路径：窗口只有工具窗口一种形态。声明 `DockSide.Center` 的模块窗口
仍落在中央工作区，但以中央页形态呈现——位置不变，变的是身份。模块代码与用户布局都无需处理，
已保存的文档页节点在恢复时自动重建为工具窗口。取消原因、迁移与已知缺口见
HistoryAurora 现行合同 `../2026-026-HistoryAurora/b-Office/current/HistoryAurora_UI风格与嵌入页面规范.md`
的「窗口形态」一节。
3.11.2 恢复参数候选的连续推进：提交参数名后显示注册的允许值/常用值，提交参数值后继续到下一个参数；
不改变文本或光标的位置参数结构提示会立即关闭，避免候选无限重弹。

# HistoryVulcan 项目概览

更新日期：2026-08-31

## 一句话定义

HistoryVulcan 是 OneHistory 的通用 .NET 8 / WPF 壳：命令、停靠、日志、设置、模块、MCP/Web
与服务生命周期。它是**独立 git 仓库**里的一个编号项目，不是共享裸仓上的一条分支。

## 项目库编码（一项目一仓）

- 本目录 `2026-023-HistoryVulcan` 本身就是仓库；默认分支是 `main`。平行开发在本仓内开分支。
- 邻接的 `YYYY-NNN-*` 目录是别的项目、别的仓库。不得把它们当成同一 Git 身份下的 worktree 或兄弟分支。
- 模块发现只认固定运行区文件系统：只枚举 `%AppData%\HistoryVulcan\Modules` 的直属模块目录。
  发现不依赖任何裸仓、不读取兄弟仓的 git 对象。
- CI 与门禁只验证本仓库。兄弟项目在本地磁盘上存在，不表示它们属于本仓，也不得用跨仓 `ProjectReference`。

## 目标与边界

### 目标

- 提供可运行、可测试、可回滚的独立宿主，并为嵌入式消费保留固定公共合同。
- 单一窗口承载中央工作区与四边工具页；布局持久化；模块可热重载。
- 默认最小能力、安全边界、公开 API 基线守住冻结契约。

### 范围

- WinExe 宿主与同目录 Console CLI，以及本仓仍维护的 `Core`、`Services`、`ServiceHost` 合同；桌面 Shell 在 HistoryAurora。
- 根级 `b-Code-Tests`（`HistoryVulcan.Tests`）。
- 消费合同编辑源、候选打包、正式归档及 `z-Publish` 当前快照。

### 非目标

- 不承载 Janus、Mercury 或其他模块的业务与数据模型。
- 不提供已删除的数据库服务、通用表窗口或 `db.*`。
- CI 不发布、不打标签、不部署。
- 不把项目库 Git 治理做成宿主职责（那是 Janus，且存储引擎正在换到一项目一仓）。

## 3.11.2 Completion Addendum

Focused-console completion continues after method selection through registered parameter names and values. Committing a parameter name immediately recomputes its allowed/common values; committing a value advances to the next parameter and closes when no candidate remains. A structural parameter hint that changes neither text nor caret closes without recomputation, preventing an infinite popup loop. This is a Shell-only state-machine fix; Core, CommandBus, parser, and command registration contracts remain frozen.

## 3.11.1 Interaction Addendum

`vulcan.app.focusconsole` is registered in both the service and frontend command registries. The service relays the semantic command when the frontend is connected and otherwise starts the frontend with `--focus-console`; startup executes the same semantic command. The frontend shows and activates the shell, focuses console input, and maximizes the console tool window.

Console completion follows domain -> class -> method -> parameter. Tab confirmation of a domain, class, or method immediately recomputes the next candidate layer; candidates support case-insensitive exact, prefix, and contains ranking.
The assistant is active only while the console is the maximized/focused page. In normal docked layout, typing and Tab stay with ordinary WPF console input: no popup, command-catalog switch, selection movement, or selection commit. `vulcan.command.show` returns additive command annotations together with existing parameter metadata so consumers can interpret registrant-owned completion providers. This is Shell-internal routing and must not change the frozen Core/CommandBus contract.

### REQ-CMD-010 指令分类法：三段业务指令与两段直接方法（3.4.0，DEC-025）

- 目的：让「域|类|方法」模型只有两种合法形态且判定纯结构化，使目录筛选、控制台补全和
  MCP schema 三处共用同一套判定，不再为影子域留特例路径。
- 要求：
  1. 合法形态恰有两种，全小写、无连字符、不留别名：
     - **三段 `<域>.<类>.<方法>`** —— 业务指令的默认形态；
     - **两段 `<域>.<方法>`** —— 该域的**无类直接方法**，为「插一条快捷方法」保留，
       不属于任何类。
  2. 类推导是纯结构式判定，不做语义猜测：
     段数 ≥ 3 取第二段为类；段数 = 2 判为无类（**不再回退首段作为类**）；
     描述符显式声明的 `CommandClass` 永远优先。
  3. `vulcan` 域内置**三段**指令归入十类：`app`、`cli`、`command`、`ui`、`log`、`mcp`、
     `module`、`prompt`、`svc`、`web`。`cli` 仅承载本地 CLI 自发现；其他新增内置三段指令必须并入既有类。
     内置直接方法（两段）不受十类约束，但同一域的直接方法超过 5 条时应重新评估是否建类。
  4. 「无类」是受控的显示类别：目录与命令集的类筛选含「无类」项，
     该标签只用于显示，不参与类推导。
  5. 不存在没有所有者的域。内置指令域恒为 `vulcan`，模块域由 owner 强制（见 REQ-CMD-011）。
  6. **已注册域是绝对名解析的唯一权威源**：`CommandRegistry` 暴露全部已注册命令名首段的集合，
     随模块装载/卸载动态变化。任何组件都不得硬编码域名字面量。
- 影响面：任何仍在注册两段式指令的消费方，其命令按第 2 条从「类.方法」改判为
  「域的直接方法」，归类显示变为「无类」。命令名与调用方式不变，其首段同时成为已注册域
  并参与绝对名解析。OneHistory 体系内已无此类消费方——本条只对体系外的独立仓库适用。
- 验收：`CommandTaxonomyContractTests` 断言运行期注册表内每条指令都是两段或三段、
  域 ∈ {`vulcan`, 模块域}、三段指令的类 ∈ 十类、两段指令判为无类；
  `vulcan.command.domains` 只报 `vulcan` 与已装载模块域。
- 关联组件：`HistoryVulcan.Core/Commands/CommandRegistry`、各 `BuiltinCommands.*`
- 关联验证：`VERIFY-FULL`

### REQ-MOD-008 按模块卸载必须清空该模块的全部快照登记（5.2.1，DEC-059）

- 目的：让「热装一个已装载的模块」只接入一次，指令面等于新包的实际指令面。
- 背景：`UnloadFromSnapshot` 清了 `RegisteredNames` / `PendingCommands` / `Metas` /
  `Modules` / `ContextsByOwner`，唯独漏了 `PendingAttach` 与 `AttachFailures`。

- 要求：
  1. 「一个模块在快照里留下哪些痕迹」只写一处：`Snapshot.ForgetModule(owner)`

     后者由注册表消费线程改写，不得在未编组的回滚路径上顺手动。

  4. 不在 `AttachPhase` 接入后移除条目：`AnnounceReady` 把 `PendingAttach` 当作

### REQ-A4 服务进程摆脱 WPF（4.0.0，DEC-049）

- 目的：服务进程从来没有窗口，此前依赖 WPF 只是为了拿一个 `Dispatcher` 当「排到主线程」
  的队列，代价是整个工程 `UseWPF` 并拖入 PresentationFramework 等整套 UI 程序集。
- 要求：`HistoryVulcan.ServiceHost` 不得 `UseWPF`，不得引用 `System.Windows`。消息循环由
  `ServiceRunLoop` 承担，装成 `SynchronizationContext` 后供 `CommandBus.UiContext` 与
  `ModuleHost.UiContext` 使用。`TargetFramework` 保留 `net8.0-windows`——自启动注册表等
  Windows API 仍需要它，这与是否 `UseWPF` 是两件事。
- 要求（语义对齐，本条重点）：替换实现必须保住被取代者的三条语义，否则症状是模块里
  罕见难复现的竞态而非构建错误：
  1. **回调彼此串行且不重入**——模块据此假定投递到 `UiContext` 的回调不并发；
  2. **单个回调抛异常不终结循环**——与 WPF 未处理异常被 App 级处理器吞掉后继续泵消息一致，
     否则一个坏模块能拖垮整个服务进程；
  3. **循环线程上的同步投递直接执行**——与 `Dispatcher.Invoke` 一致，避免自锁。
- 要求：`requestStop` 自带「排到循环上再关」的语义。命令处理器跑在线程池上，同步关停会让
  循环在响应写回之前排空退出。
- 说明：不实现 WPF 的优先级队列。原先唯一用到优先级的地方是把延迟启动任务排在
  `ApplicationIdle`，其真实意图是「排在已入队的启动工作之后」，FIFO 队列天然满足。
- 验收：`ServiceRunLoopTests` 七条用例覆盖上述三条语义、退出码传播、关停后投递被丢弃、
  以及 `SynchronizationContext` 落到同一条串行队列；`ServiceHost` 与 `ServiceCommands` 内
  不再出现 `System.Windows`；ServiceHost 输出目录不含 `PresentationFramework` / `WindowsBase`。
  真机冒烟：无 WPF 循环下 `/api/health` 为 `shells=1`，命令与模块中继正常。
- 关联组件：`HistoryVulcan.ServiceHost/ServiceRunLoop.cs`、`ServiceHost.cs`、`ServiceCommands.cs`
- 关联验证：`VERIFY-FULL`

## 系统架构

### 系统边界

HistoryVulcan 管理通用框架能力和扩展合同，不拥有消费应用的业务模型。Core 不依赖 WPF；Services
实现通用服务；HistoryAurora 是唯一直接封装 AvalonDock 的层；ServiceHost 提供用户会话无窗后台进程。资源浏览/文件
操作不属于 HistoryVulcan，未来由独立模块提供。

### 组成

| 组件 | 路径 | 职责 | 主要输出 |
| --- | --- | --- | --- |
| Core | `b-Code-HistoryVulcan/HistoryVulcan.Core` | 注册器与命令总线契约（命令、日志、MCP、存储） | `OneHistory.HistoryVulcan.Core` |
| Services | `b-Code-HistoryVulcan/HistoryVulcan.Services` | 设置、文件状态、日志、MCP、模块实现 | `OneHistory.HistoryVulcan.Services` |
| HistoryAurora | 外部项目 | WPF 主壳、停靠 UI、控制台、面板与模块管理 | 不在本仓维护 |
| ServiceHost | `b-Code-HistoryVulcan/HistoryVulcan.ServiceHost` | 无窗服务宿主和 `svc.*` 生命周期 | `OneHistory.HistoryVulcan.ServiceHost` |
| App | `b-Code-HistoryVulcan/App` | 单 EXE 前端/后台入口与 GUI 验收宿主 | win-x64 framework-dependent ZIP |
| Tests | `b-Code-Tests/HistoryVulcan.Tests` | 公开合同、安全、布局与冻结回归 | TRX 与进程退出码 |

### 关键流程

1. 消费方固定包版本，使用 HistoryAurora 的配置显式启用需要的模块或 MCP 能力。
2. 普通 EXE 启动 WPF 前端；`--service` 启动后台权威宿主，前端通过 loopback 发布 UI 命令目录并接收中继。
3. HistoryAurora 组装日志、布局和窗口；模块通过注册合同增加命令与工具页；全局快捷键只向后台命令总线提交命令文本。
4. 模块候选由宿主 `vulcan.dev.submit` / `finish` 写入 `z-Publish/HistoryX-vX.Y.Z/`；宿主自身候选由 `vulcan.release.cycle` 写入平铺 `z-Publish/host/`。CI 不发布。Diana 不发布。

### 不变量与生成物边界

- Core 保持零 WPF 依赖；AvalonDock 只从 HistoryAurora 直接引用。
- 所有命令执行进入同一总线；危险命令进入统一确认边界。
- 正式包和 Z 级快照不直接编辑；权威源是源码、`b-Office/package/` 与发布模板。
- HistoryAurora 只保留 `ModulesView` 这一套模块管理页面；独立 HistoryVulcan 可执行宿主显式启用
  `EnableModules` 并成为模块生命周期所有者。Janus 只提供停靠位置与消费配置，后续业务能力以模块接入，
  不复制页面或第二个 `ModuleHost`。
- 3.1.1 删除内置资源浏览能力和演示电机页面；`res.*`、`motor.*` 不再注册。
- `bin/`、`obj/`、`artifacts/` 是可重建生成物。
- `z-Publish/` 根候选与 `history/` 直属历史包是发布资产。

## DEC-059 按模块卸载必须抹干净，清单只写一处

- 状态：已接受
- 日期：2026-09-05
- 版本：5.2.1
- 背景：对 HistoryDiana 跑 `vulcan.dev.submit` / `vulcan.module.install`，回执写「已热重载到
  活宿主」，而 `vulcan.module.list` 显示新版本号 2.5.0、`instanceId` 已变、`attached=false`、
  `commandCount` 仍是旧的 18，`attachFailures` 只有一句
  `模块 HistoryDiana 重复暂存指令: diana.docs.catalog`——那是该模块字母序最靠前的指令，
  说明整份指令集都撞了。
  根因是 `UnloadFromSnapshot` 漏清 `PendingAttach`（与 `AttachFailures`）：
  快照里同时留着旧条目和新条目，`AttachPhase(onlyOwner)` 于是接两遍，
  第一遍用**已卸载 ALC 的旧类型**把旧指令面注册回去，第二遍撞重名抛异常。
  重装同一个包不能自愈：内容一致会短路（「内容一致，无需替换」），内容不同则再多攒一条。
  唯一的恢复手段是重启宿主——而模块开发管线的前提恰恰是不许停宿主。
- 决策：
  1. 新增 `Snapshot.ForgetModule(owner)`，独占「一个模块在快照里留下哪些痕迹」这个答案：
     `PendingAttach` / `Metas` / `AttachFailures` / 指令计数 / `ContextsByOwner`，
     并交出该模块的加载上下文。
  2. `UnloadFromSnapshot`（`vulcan.module.unload` / `install` / `remove` 的必经之路）与
     `TeardownAddedModule`（单包装载失败回滚）都改为经它，不再各列一份清单。
  3. 指令表与 `Modules` 明确留在各调用方，并在 `ForgetModule` 的注释里写明理由，
     避免下一个读者以为那是又一次遗漏。
- 为什么收口在卸载侧，而不是装载侧或接入侧：
  - **装载侧按 owner 替换**会砍掉合法形状——`LoadGroup` 下同一目录多个程序集声明同一模块名时，
    一个 owner 本就允许有多条 `PendingAttach`，每条带自己那份 `Types`。
  - **接入后移除条目**会打断 DEC-057 的就绪通知：`AnnounceReady` 把 `PendingAttach`
    当作「本轮装了哪些模块」的名册来算 `<域>.host.ready` 钩子，清掉等于钩子全部不发。
  - 卸载侧则是这条不变量的唯一破口，而且它已经有一份写对了的孪生实现
    （`TeardownAddedModule` 一直有 `PendingAttach.RemoveAll`）——两份清单同时存在、
    只有一份写全，正是这个缺陷的形状。收口成一处之后这种偏差不再可能。
- 这是同一类错误的第三次：`ModuleHostContextTests` 里那条「三条拆除路径一条都不能漏」的用例
  记着前两次（整快照重载不回收实例、按模块卸载只丢引用不 Dispose），两次都是**少覆盖了一条路径**。
  本轮不是少覆盖路径，是同一条路径上少抹了一项状态；对策相同——把「该抹哪些」从两处收成一处。
- 顺带修掉的潜伏问题：`AttachFailures` 此前也不清。一个模块只要接入失败过一次，
  之后即使装成功，`ReplaceModuleMeta` 仍会读到旧的失败原因，`attached` 永远是 false。
- 与冻结的关系：属于冻结合同 §4 第二类「正确性缺陷修复」。`Snapshot` 是私有嵌套类，
  三份 Shipped 与三份 Unshipped 一个符号未动，`public-api-baselines/5.2.1/` 与 5.2.0 逐字一致，
  冻结标签仍是 `v5.1.2`。
- 后续（不在本轮，落在别的仓）：见验证合同 5.2.1 一节记录的两条只读性投影不一致——
  `aurora.command.runreadonly` 对整个后台指令面失效（2026-026-HistoryAurora），
  以及 MCP 工具表里按名字排除整段 `vulcan.module.*`（网关侧）。
  后者是 DEC-058 刚判过死刑的那类名单式规则的最后一份存量，只是它活在宿主看不见的地方。

## DEC-058 指令总线只解析一次；按名字写死的规则一律退役

- 状态：已接受
- 日期：2026-09-04
- 版本：5.2.0
- 背景：宿主质量本身不差，但内核积了两类冗余。其一，**一行指令被解析五次**——回显脱敏、
  分类、执行、结果脱敏、载荷风险判定各 `CommandParser.Parse` 一遍，各配一个
  `catch (CommandSyntaxException)`，于是「语法错误时该怎么办」在五处各答一次。
  其二，一批**再也走不到的分支**：按名字写死的两条已退役命令、只剩测试在维持的公开成员、
  自 3.2.1 起就注明「装载路径不再调用」的方法。
- 决策：
  1. 总线解析一次，结果随 `Request` 走完全程；语法错误只判定一次。
  2. 脱敏的**名单式规则全部改成判据式**。原先写死 `vulcan.web.token` / `vulcan.mcp.token`
     两个名字（分别在 3.13.0、4.4.0 就已不存在），改为把既有的敏感名判据用在命令名上——
     覆盖任何 `*.token` / `*.secret`，且没有名字需要维护。
  3. 解析失败时不再用正则逐个遮参数，直接遮掉命令名之后的整段。
  4. 删掉十个零消费方的公开成员（清单见消费变更摘要）。
- 为什么名单式规则必须退役：冻结合同第 4 节已经记过一次同样的教训——`McpExposurePolicy`
  按名字写的硬排除失配过四次，每次都是指令改了名而规则还盯着旧名字。
  脱敏里这份名单是同一个错误的最后一份存量，而它守的是**密钥**，失配的代价比目录错乱大得多。
- 为什么敢删这十个成员：逐个查过三处——宿主源码、测试，以及**七个已部署模块的二进制**
  （在运行区模块目录下按元数据符号名比对）。十个成员在三处都是零引用。
  这不是「大概没人用」，是逐一核对过的。
- 与版本号的张力（明确记下，不掩盖）：冻结合同第 5 节写的是「删除或签名变更必须进消费变更摘要
  **并走主版本号**」。本轮走的是 5.2 而不是 6.0，理由是十个成员的实测消费方为零，
  破坏面为空；代价是这条规则被开了一个口子。**下一轮若再有删除且消费方非空，必须走主版本号。**
- 后果：净减 179 行、Core/Commands 由 13 个文件收到 11 个（三个命名助手合并为 `CommandNaming.cs`）。
  公开面净减 10 条，无任何新增。

## DEC-057 模块按声明依赖接入，并给出可询问的就绪点

- 状态：已接受
- 日期：2026-09-04
- 版本：5.1.3
- 背景：5.1.2 及以前，一轮装载的时间线是「扫描时逐个 `Attach`，全部扫完后**一次性**把所有
  模块指令换进活登记表」。两件事之间隔着整轮装载：先接上的模块已经在跑，而它要调用的其它
  模块的指令一条都还没登记。界面模块在 `Attach` 里就开自己的线程，因此它拉命令目录、向各
  模块要页面描述的时刻不由宿主决定——窗口有多长取决于剩余模块的装载耗时。
  现场证据：冷启动日志里 `HistoryAurora` 接上后 140 毫秒内连续 `vulcan.command.list`，
  每次只看到 37 条框架指令；另有成片的 `未知指令: aurora.ui.actions`、
  `未知指令: janus.proj.list`。表现就是用户报的「启动有几率加载不出来几个模块」。
- 决策：把装载拆成两段，并给出一个完成点。
  1. **装载阶段**只读程序集、收反射指令，不接入任何模块。
  2. **接入阶段**按 manifest 声明的 `dependsOn` 排序逐个 `Attach`，每接上一个立刻登记它的
     指令。于是任何模块 `Attach` 时，排在它前面的模块指令都已可调用。
  3. 全部接上后置就绪，并按命令名通知声明了 `<域>.host.ready` 的模块；
     `vulcan.module.ready` 让任何消费方可以直接问「现在这张目录算不算数」。
- 边界：
  - `dependsOn` 只影响**接入次序**，不是硬前置。依赖缺失、依赖成环、依赖自己都只记发现诊断，
    模块照装——「排不出次序」不该等于「谁都不装」。宿主不替模块决定少了谁就不能跑。

## DEC-050 指令域跟随实现方，不跟随历史归属

- 状态：已接受
- 日期：2026-08-19

  而把两条一起搬进 Aurora，就会为一条纯总线能力在 `aurora` 域下造一个不该存在的名字，

- 兼容：`vulcan.command.run` 命令名、参数、相对路径基准（`%AppData%\HistoryVulcan`）
  全部不变，用户脚本无感。`vulcan.command.copyexample` 是破坏性改名，进消费变更摘要。
- 替代条件：只有重新规定"域名标识历史归属而非实现方"的同级决策可以替代。

## DEC-046 本机 IPC 通道必须持券，回环不构成边界

- 状态：已接受
- 日期：2026-08-18
- 背景（实测）：在 3.12.1 运行中的宿主上，一个普通本地进程不带任何令牌，只加
  `X-HistoryVulcan-Client: Shell` 头 POST `/api/command`，即可在权威总线上执行命令（实测
  `vulcan.command.domains` 返回 HTTP 200）。该路径**没有任何 MCP 限制层**，因此 MCP 侧的硬排除
  ——`vulcan.app.quit`、`vulcan.module.install/remove`、全部 12 条 `vulcan.mcp.*`——在同机范围内
  可被整体绕过。MCP 自己的令牌还是可选的（未配置时完全不校验）。这是既有状况，不是 DEC-045 引入的。
- 决策：`WebGateway.Start` 用密码学随机数生成一枚 32 字节一次性凭据 `AccessToken`，`Stop` 时清空；
  `Authenticate` 要求回环、`ClientKind.Shell`、持本次凭据三者同时成立，缺一返回 401。凭据由
  `ServiceHost` 写入 `endpoint.json` 的 `accessToken` 字段，前端经既有的
  `ShellEndpointProfile.AccessTokenProvider` 携带。凭据不落设置、不可配置、不回显、不写日志。
- 原因：回环不是边界。前两个条件（回环、请求头）任何本机进程都能满足或伪造，只有凭据能区分
  "我们自己启动的前端"和"任意本机进程"。在合并网关之前必须先有这条真实边界，否则合并等于把一条
  文档上写着、实际不存在的边界固化进结构。
- 边界与残余风险：这条边界的实际强度等于 `%AppData%\HistoryVulcan\service\endpoint.json` 的读取
  权限。以当前用户身份运行的进程仍可读取该文件并取得凭据——这是本机同用户威胁模型下的固有上限，
  本决策不声称解决它。真正的收益是：**默认不再对任意本机进程敞开**，且宿主重启即换券。
- 连带修复（真机启动发现）：前端派生后台后的等待循环原先只判 `endpoint.json` 是否可读，
  而服务被强杀时来不及删除该文件，残留记录端口有效、`accessToken` 为空，循环第一轮即误判就绪，
  前端拿空凭据连新服务、稳定 401 后转本地模式（`/api/health` 显示 `shells=0`）。
  修法：连不上既有后台时先删除该记录再派生，等待条件改为「端口有效**且**凭据非空」
  （`App.IsUsableEndpoint`）；`AccessTokenProvider` 改为每次调用现读 `endpoint.json`
  而非捕获快照，使后台重启换券后前端能自行恢复。此缺陷在 3.13.0 前是潜伏的——端口恰好相同
  且后台不校验令牌，连上了就看不出来；补上凭据校验后它变成硬失败。
- 验收：`FreezeBlockerTests.GatewayAcceptsOnlyTheLoopbackShellSession` 覆盖伪造 Shell 头无券、
  持错券两种拒绝；`AccessTokenIsRegeneratedPerListenAndClearedOnStop` 覆盖每次监听换发与停止清空；
  `ServiceEndpointHandshakeTests` 覆盖残留/空券/无端口记录均不可用。
  真机冒烟：残留 endpoint.json 条件下启动，`/api/health` 须为 `shells=1`，
  无券请求 401、持券 200，重启后令牌改变。
- 替代条件：只有更强的本机进程身份验证（如命名管道 + 进程令牌校验）可以替代本决策。

## DEC-045 删除局域网面，Web 网关退回纯本机 IPC

- 状态：已接受
- 日期：2026-08-18
- 决策：`WebGateway` 只监听 `127.0.0.1`，只接受声明 `X-HistoryVulcan-Client: Shell` 的同机前端。
  删除设备鉴权与配对（`IDeviceAuthenticationProvider`、`IDevicePairingProvider`、
  `DeviceAuthenticationResult`、`DevicePairingResult`、`/api/pair`、`ShellServiceClient.PairAsync`）、
  令牌鉴权、绑定地址配置、CORS、按会话/按源限流，以及从未注册的 `WebCommands`
  （`vulcan.web.bind/confirm/cors/status/token` 五条命令随之消失）。

  一并退役；`web.port`、`web.portretries`、`web.frontendcatalog*` 保留。
- 证据：删除前该能力在生产代码中没有任何装配点——`WebGateway.DeviceAuthentication` 只在
  `FreezeBlockerTests` 里被赋值过；`WebCommands.RegisterAll` 全仓无调用点，运行时注册表实测
  81 条 `vulcan.*` 命令中没有 `web` 类；`ServiceHost` 的局域网确认分支读的是设置键 `lan.confirm`，
  而唯一能写确认档的 `WebCommands` 写的是 `web.confirm`，两个键从不相交，该分支在任何配置下
  都只返回 false。
- 原因：一套两年没有消费方、鉴权入口只有测试在用、确认路径因键名错配而不可达的"安全边界"，
  留着只会让每次公开面评审多背一份负担，并掩盖真实的可达攻击面。
- 代价与边界：失败鉴权不再有节流（原按远端地址限流随之删除）。在只监听回环的前提下可接受——
  能对回环发请求的人已经以当前用户身份在执行代码。**一旦将来重新对外监听，限流必须与监听
  能力同时回来**，不得只恢复监听。
- 未尽项：`WebGateway.RequestWebConfirmation` 与 `/api/confirm` 保留未删。前端
  `ShellServiceClient` 仍有 `confirmation` 的 WebSocket 处理器，但 `ServiceHost` 侧唯一的调用
  条件（源以 `Web:` 开头）已不可达，形成一条挂空的确认通道。留待网关合并（单监听器）时
  连同确认路由一起定夺，不在本次删除范围内。
- 替代条件：只有基于合并后单网关重新定义的远程访问协议可以替代本决策；不得原样复活本次删除的机制。

## DEC-041 消费文档回到本仓 z 快照并入库（撤销 c9d2e90 的移除）

## DEC-038 3.11.2 参数候选连续推进且必须有进展

聚焦控制台提交域、类、方法、参数名或参数值后，只要命令文本或光标实际前进，就立即重算下一层候选。
参数名因此可以进入注册的允许值/常用值，参数值可以进入下一个参数；值位于行尾时补一个空格作为下一层边界。
若位置参数结构提示的插入文本为空、文本与光标均未变化，则关闭 Popup 且不重算，阻断无限重弹。
该决策仅调整 Shell 内部补全状态机，不修改 Core、CommandBus、解析器或注册协议。

## DEC-037 3.11.1 命令助手只在控制台聚焦布局启用

控制台 Popup 命令助手只在控制台最大化/聚焦布局启用。普通停靠布局中的字母与 Tab 保持普通输入语义，

`CommandCatalogDetail.Annotations` 作为 Shell DTO 的兼容增量传递注册注解。Core、CommandBus、解析器与命令注册协议不变。

## DEC-025 3.4.0 无类直接方法回归、域聚焦与注册域权威源

- 状态：已接受
- 日期：2026-08-10
- 取代：DEC-023 第 1 条中「「无类」概念一并废止」与「所有内置指令一律三段式」两句。
  DEC-023 的其余内容（九类命名、模块域去品牌前缀、门禁解耦、无人工交互）继续有效。
- 决策：分四条同时生效。
  1. **无类直接方法正式回归，成为受控类别**。命令名允许两段 `<域>.<方法>`，
     表示「该域的直接方法」，不属于任何类。三段 `<域>.<类>.<方法>` 仍是业务指令的默认形态。
     判定规则改为纯结构式：段数为 2 即无类；段数 ≥ 3 取第二段为类；
     描述符显式声明的 `CommandClass` 永远优先。
     两段名不再回退首段作为类——`arena.cell` 从此读作「域 arena 的直接方法 cell」，
     而不是「类 arena 的方法 cell」。
  2. **注册域是绝对名解析的唯一权威源**。`CommandRegistry` 暴露已注册命令名首段的集合，
     域清单随模块装载/卸载动态变化，任何地方都不得硬编码域名字面量。
  3. **域聚焦（domain focus）**。控制台输入可聚焦到某个域；聚焦期间：
     - 输入首段命中**已注册域**时按绝对名解析，不拼前缀；
     - 否则自动补上当前聚焦域前缀。
     因此 `mercury.go`、`vulcan.*` 等在任意聚焦状态下都能直接输入，
     无需每个域各自提供一条退出指令。聚焦状态与控制台域筛选下拉双向同步，
     下拉选「全部」即退出聚焦。
  4. **补全按域 → 类 → 方法 → 参数分段推进**，不再一次性平铺全名候选。
     参数候选只能来自模块注册时提供的 `ParameterSpec`，宿主与 Mercury 都不得猜测参数名。
- 原因：
  1. 上一轮把无类一并废止是矫枉过正。域的直接方法是一个真实且长期需要的类别——
     它给「插一条快捷方法」留出位置，而不必为一两条命令硬造一个类。
     受控地保留它，比让每个模块各自发明变通更可控。
  2. 绝对名脱固若依赖硬编码域清单，每接入一个新模块都要改宿主，
     这正是 DEC-023 第 3 条要消除的那种跨仓库耦合。
  3. 退出域聚焦如果做成每个域一条退出指令，会让每个模块都被迫耦合一份与自身业务无关的命令；
     用「首段是已注册域就按绝对名解析」这一条规则，退出能力自然涌现，零新增指令、零域耦合。
- 后果：
  - **影响面**：仍在注册两段式指令的消费方，其命令从「类.方法」改判为「域的直接方法」，
    在命令集与控制台里改为「无类」分组显示。命令名与调用方式不变，只是归类显示改变；
    其首段同时成为已注册域，参与绝对名解析。
    OneHistory 体系内已无此类消费方，本条只对体系外的独立分支适用。
  - 命令集与控制台恢复「无类」筛选项；DEC-023 删除的 `NoneLabel` 以受控形式回归，
    但只作为显示标签，不再承担类推导逻辑。
  - `mercury.go` 是无类直接方法的第一个正式用例：`mercury.go <域>` 进入聚焦，
    `mercury.go` 无参退出。
- 替代条件：若某个域的直接方法超过 5 条，应重新评估是否该为它们建类。

# HistoryVulcan 宿主冻结合同

> 当前生效版本：**5.1.2**　冻结标签名：**`v5.1.2`**　重新冻结日期：**2026-08-31**
>
> 本文是 HistoryVulcan 宿主公开面与模块接入面的稳定性承诺。冻结的是**契约**，不是代码——
> 内部实现可以重构，消费方看得见的注册器、命令总线、开发/发布总线与公开 API 必须守住。

## 1. 为什么要有这份合同

冻结之前，改 Vulcan 是一件昂贵的事：Core 的公开面里混着大量只服务于单一模块的类型，
于是模块的正常演进被迫触发宿主的版本事件，而宿主的稳定诉求又让模块每次改动都要走
完整门禁。两头都坏。

八个版本的公开面增量显示，推动 Core 增长的从来不是地基本身：

| 来源 | 累计推动 Core | 实质 |
| --- | --- | --- |
| `Core.CommandSurface` | 79 行 | 控制台命令目录（单一模块消费） |
| 全局快捷键 `Core.Input` | 46 行 | 「按键 → 命令名」，载荷本就是命令 |
| 声明式面板 `Core.Panels` | 38 行 | 注定生长的数据 schema，零模块消费 |
| 命令工作台 `Core.Modules` | 15 行 | 单一模块的挂载点 |

这些已全部清出。Core 已发布面从 512 行降到 362 行，减少 29%，**且没有任何例外条款**。

## 2. 冻结范围

| 程序集 | 承诺 | 门禁 |
| --- | --- | --- |
| **HistoryVulcan.Core** | 5.1.2 重新冻结；模块注册器与命令总线是长期接入面 | Shipped 基线 + 质量门禁 |
| HistoryVulcan.Services | 5.1.2 冻结；只保留宿主服务与开发/发布总线合同 | Shipped 基线 + 质量门禁 |
| HistoryVulcan.ServiceHost | 5.1.2 冻结；无头组合、CLI/运行时入口保持稳定 | Shipped 基线 + 质量门禁 |

5.0 起不再有 `HistoryVulcan.Extensibility`。能用命令名表达的联动走命令总线；活对象走 `CommandResult` 载荷，由认领方解释。

## 3. Core 里现在有什么

| 命名空间 | 内容 | 为什么冻得住 |
| --- | --- | --- |
| `Commands` | 总线、注册表、描述符、上下文、结果、解析；`DomainFocus` / `CommandClassLabels` | 全体模块的集成面 |
| `Modules` | `ModuleInfoBase`、`IModuleContext`（仅 Bus + RegisterCommands）、`IModuleContextAware`、`IDeferredStartupWork` | 注册器与指令暂存 |
| `Logging` / `Storage` | 日志与设置契约（供宿主与开发总线，不注入模块） | 宿主内部消费 |

5.0 已删除 `Clients`（`ClientKind` / `ClientSession`，会话身份由 Portunus 自持）与 `Mcp`（远端可见性走总线上的 `HiddenReason` / `Level` / `Readonly`）。

5.0 起本节由 DEC-052 替代：宿主不再冻结 MCP 安全面或客户端会话类型。远端可见性看总线标志；会话身份由 Portunus 自持。

## 4. 什么情况下允许动宿主冻结面

冻结不是"永不修改"，而是"修改需要理由，且理由要写下来"。允许的情形只有三类：

1. **安全缺陷修复**——包括审计、确认、暴露策略的漏洞。
2. **正确性缺陷修复**——公开面语义与文档不符，且文档是对的。
3. **新增全体模块都需要、且不属于任何单一消费方的能力**——需同时满足下述判据。

### 新增判据（必须全部满足）

- **至少两个模块需要它**，且一年后仍然成立；
- **无法用命令名表达**——凡是能走命令总线的联动，一律走命令总线（见 `CommandBus.InvokeAsync`）；
- **不是任何单一消费方的展示、协议或便利功能**。

任何一条不满足，它就不该进 Core：用命令名表达，或由认领该命令的模块解释载荷。

### 明令禁止

**不得再向 `CommandDescriptor` 增加字段。** 本类历史上为每个消费方各长过一个字段
（`Domain`/`CommandClass` 用于目录展示、`AllowMcpExecution` 用于 MCP、`ExecutionSite`
用于前端路由、`SupportsUndo` 是从未实现的预留位）。后两个已经删掉——`SupportsUndo`
接线至今零行为，`ExecutionSite` 在界面变成宿主内模块后全仓无人置为 `Frontend`，
它的四个读取点都是永远走不到的分支。

4.8.0 又收掉一组：`Dangerous`、`ConfirmPrompt`、合成属性 `IsDangerous` 三个成员
表达的是同一件事——「执行前要不要问人」。三份表达意味着不同消费方各读各的
（MCP 读合成属性、总线读闸口、目录读元数据），于是同一条指令在不同的面上
可以给出不同答案。现在只剩两个：`Level` 是唯一权威，`ConfirmPrompt` 只提供文案。
两者不一致时注册表拒绝注册，因为「写了文案却没升级别」的后果是闸口静默消失，
那是最不该靠人记住的一类错误。

同一轮还收掉了 `AllowMcpExecution` 与 `AllowCliExecution`：那是「给每个消费面各发一个
令牌」，而**暴露与否只该有一处声明**。现在是 `HiddenReason`——写原因即隐藏，不写即暴露，
理由本身就是唯一能让后来人判断该不该继续隐藏的东西。它同时取代了 `McpExposurePolicy`
里那份按名字写的硬排除名单：那份名单失效过四次，每次都是指令改了名而规则还盯着旧名字。

至此描述符上的声明位是四个：`Readonly`（改不改东西）、`Level`（问不问人）、
`ConfirmPrompt`（问的时候说什么）、`HiddenReason`（暴不暴露）。

新的消费方能力一律走 `CommandDescriptor.Annotations`，键为 `<消费方>.<能力>`，
例如 `mcp.execute`、`catalog.hidden`。总线只负责原样携带，消费方自行定义与解释自己的键。

这条规则是整份合同能长期成立的关键：清理存量只解决一次，堵住增量才解决长期。

## 5. 变更流程

1. 对照第 4 节判据自查；不满足即改投演进层。
2. 满足则升版本，在 `b-Code-Eng/public-api-baselines/<版本>/` 建立批准基线。
3. 已发布面的移除或签名变更必须以 `*REMOVED*` 显式声明，不得静默删除。
4. 走完整发布管线（`vulcan.release.cycle`）：宿主合同、单元测试、质量门禁、
   公开 API 基线四道门禁全过方可发布。
5. 破坏性变更须在本文件追加记录，写明原因与消费方迁移路径。

## 6. 给未来的自己

半年后你会看到两个程序集，并且很可能忘记为什么。原因只有一条：

> **稳定性承诺决定归属，功能领域不决定归属。**

同样是"命令"相关的东西，`CommandBus` 在 Core 而 `DomainFocus` 在演进层；同样是 MCP

**它会不会因为某个消费方的需要而改变？**

会，就不属于 Core。

## 静态复核重点

业务 `Click`/双击处理器只构造命令文本并调用 `CommandBus`；不得直接调用日志过滤服务、停靠服务、
剪贴板或文件选择服务。命令处理器可以持有这些系统交互，以保证手输、脚本、模块和 MCP 使用同一描述符与回执，
但必须满足本文开头的「不得依赖人工点击」约束。

主窗口/独立浮窗的原生移动属于窗口宿主交互；浮窗拖动过程中为保持鼠标锚点而执行的几何恢复不另建命令，
但离散的最大化/还原必须使用 `vulcan.ui.floatstate`，且不得改变 HistoryVulcan 停靠模型。
普通真实页签拖出沿用 AvalonDock 原生停靠流程；专注真实页签改变布局时必须依次执行
`vulcan.ui.restore` 与 `vulcan.ui.float`。空白顶栏不得推断停靠目标或触发页面拖出。
