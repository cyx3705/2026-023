# 7.0.0 更新：模块就是 NuGet 包

> 已接受，2026-10-11，DEC-074。行为以 `b-Office/current/技术合同.md` 为准。
> 冻结基线仍是 **v6.0.0**。公开 API 不因换容器而变。
> 6.0.0 已按 DEC-071 收口统一模块契约。本稿只改模块的容器：发布、本机消费、宿主装载用同一个 nupkg。

## 结论

模块打出来的包就是宿主装进去的包。管线按 `package.files` 自己写成 nupkg（不用 `dotnet pack`，版本字符串含 `v` 前缀时也能原样留下），这个文件直接归档、直接放进运行区、直接由宿主读取。不再先把构建输出抄成一套自造目录，再整槽复制到 `%AppData%\HistoryVulcan\Modules\<模块名>\`。

识别方式不换。宿主仍然扫描程序集，沿基类链查找全名 `BaseVariable.ModuleInfoBase`，再对 `IModuleContextAware` 做 `Attach`。换的是字节从哪个容器读出来。

## 现在的两截

| 步骤 | 现行 6.1.1 |
| --- | --- |
| 构建 | `dotnet build` 落到输出目录 |
| 发布 | `ModuleSnapshotBuilder` 按 `package.files` 把选定文件抄进 `z-Publish` 目录快照，并写 `SHA256SUMS` |
| 安装 | 整槽替换 `%AppData%\HistoryVulcan\Modules\<模块名>\` |
| 发现 | `RuntimeModuleDiscoverySource` 只枚举该目录的直属子目录，读 `module.manifest.json`，校验整树哈希 |
| 装载 | 按 manifest 的 `artifact` / `deps` 点名，把 DLL 读进内存流，装进可回收 ALC |

本机消费和发布搬的是同一批文件，容器却是手写的目录格式：清单、哈希、入口 DLL 路径各管一截。槽位里多一个文件即判坏包。`Assembly.Location` 在内存流装载下本来就是空的，模块找随包文件靠 `IModuleEnvironment.PackageDirectory`，它指向这个槽位。

## 为什么换容器就够

`ModuleHost.IsModuleInfo` 只比对基类全名 `BaseVariable.ModuleInfoBase`。模块编译时引用哪一版承载这个类型的程序集，都能被认出来。指令是公共方法；接入是 `IModuleContextAware.Attach`。依赖解析已经按简单名在包内找 `{程序集名}.dll`。

因此宿主不需要 NuGet 插件约定，也不需要新的入口特性。nupkg 是装这些程序集的压缩包。打开它、把程序集读进现有的可回收 ALC、跑现有的扫描，模块就接上了。

## 7.0 的同一个抽象

一个模块对应一个 nupkg。这个文件同时是：

- 发布归档里的候选和正式包
- 本机运行区里的安装物
- 宿主装载时打开的包

包 id 与版本就是模块名和版本，沿用现在的字符串，不另起一套命名。程序集上 `ModuleInfoBase` 的 `ModuleName`、`Version` 必须与包身份一致，不一致则跳过，规则与现在的 manifest 身份核对相同。

从目录格式里退出的部分：

- `artifact`、`deps` 文件清单。谁是模块由扫描决定；包内程序集按简单名装载。
- 槽位上的 `SHA256SUMS`。完整性看包本身的内容哈希。
- 「运行区里一个目录、目录里散落可改文件」这种安装单元。

鸭子类型上看不到、今天由宿主直读 manifest 的三项留下，字段名和含义不变，放在包内一份固定元数据里：

| 字段 | 作用 | 缺省 |
| --- | --- | --- |
| `ui` | 离线组合不提供桌面运行时则跳过该模块 | 仍必填 |
| `dependsOn` | 只约束接入次序，不是硬依赖 | 空 |
| `pinned` | 装进默认 ALC，不热卸载 | false |

这三项不升成新的公开类型，也不写进 nuspec 的自由文本。不把它们搬进 `ModuleInfoBase`。

## 宿主改装载的那一层

发现枚举运行区里的 nupkg，不枚举子目录，也不把裸 DLL 当成模块。同名重复的包全部跳过。暂存、备份、回滚用的临时文件继续排除在候选之外。

装载从包内读取程序集字节，仍进可回收 ALC；`pinned` 的包仍进默认上下文。默认上下文不补装可卸载模块。

安装事务的对象从目录改成这一个包文件。备份没有成功，不得删掉已安装的包；接入失败恢复原来的包；提交之后才清掉旧包。没有「旧槽里的残留文件带到新包」这回事，因为安装单元里没有可残留的目录树。

热重载监听这个包文件的替换。包文件变了才重载，而不是目录里任一 DLL 被摸一下。

`PackageDirectory` 仍然是模块找随包文件的根，因为 `Assembly.Location` 继续为空。它是打开 nupkg 之后的只读内容根，供 `Path.Combine` 拼包内相对路径。它不参与发现。往这个根里写文件不改变包，下一轮装载仍读 nupkg。

必须先变成磁盘文件才能启动的随包程序（模块自带的 Worker 是已有情形），从包里取出再运行。取出的位置不是运行区里的第二个模块，发现流程也不扫描它。

数据目录不变，仍是 `%AppData%\HistoryVulcan\ModuleData\<模块名>`。装包、热重载、卸载都不动它；`uninstall purge=true` 才删。

开发管线的 submit / finish 安装的就是 pack 出来的那个 nupkg。本机热装和正式归档之间不再插入一次「按 `package.files` 抄目录」。版本对齐保留：版本 props、包版本、`ModuleInfoBase.Version` 三者一致。

宿主自己的 `z-Publish/host/` 快照不在本稿范围。

## 不变

- `IModuleContext` 的窄接口：总线、登记、只写日志、运行环境、事件、唯一前端。
- 来源盖章、指令自描述、`dependsOn` 只排序不硬失败、单模块接入失败不丢弃邻居。
- 宿主源码不出现具体模块名。
- 模块数据放在包外。

## 拍板之后才改的现行条文

本稿生效时要改写的是包格式，不是 6.0 的接入契约。对应条文：

- REQ-MOD-006 固定运行区和完整包发现
- REQ-MOD-007 里「运行区文件变化触发重载」
- REQ-TXN-001 整槽替换
- 《模块开发手册》「模块包与装卸」，以及 `publish.package.files` 的抄文件描述

6.x 的目录槽不能原样放进 7.0 的运行区。模块重新 pack。`Attach` 和指令方法不用为换容器改写。`PackageDirectory` 从「槽位目录」改为「包的只读内容根」，找包内相对路径的写法可以留着。

## 实现时的验收

这些断言已经落在本仓测试里，名称以技术合同的验收行为准：

- 发现接受 nupkg，拒绝裸 DLL 和目录槽；重复包 id 全部跳过
- 包版本与 `ModuleInfoBase` 不一致时不接入
- 安装替换包文件，失败时原包还在
- 写进内容根或丢在包旁边的文件不会变成模块的一部分
- `dependsOn` 次序、离线跳过 `ui`、`pinned` 留在默认 ALC 仍然成立
- 包文件替换触发一次热重载
