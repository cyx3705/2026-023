## 定调：开发路线归宿主（2026-08-21 议定）

指的是**完整一轮**：从主干拉出工作区 → 改 → 门禁 → 并回主干 → 删工作区。
不是部署那一小段。

**为什么不留在 Diana：关联失效。** Diana 是模块，和其余四个装在同一进程、
编译到同一份宿主快照、同一条装载路径。宿主 API 一动，Diana 和它要修的那些模块
**一起坏**——而那正是最需要修复路线的时刻。修复工具不能和被修对象共享失效域。
（就今天一个会话：Minerva 消失过、Aurora 注册 0 条指令过、Mercury 的坞没了、
Diana 管线炸两次。五个模块四个坏过。）

**顺带的账，量过：**
```
开发路线的权威 = 1504 行 PowerShell（Publish-OneHistoryModule 692 + ContractCore 414 + ...）
Diana 烟测 262 行，引用这些脚本的次数 = 0
宿主 = 129 个测试，每次构建都跑
```
那 1504 行**一行自动化测试都没有**。悬空调用能活下来不是因为"很少发布"，
是因为没有任何东西检查过它。搬进宿主改成 C# 是从零覆盖变成有覆盖。

**三个硬性限定，少一个这事就不成立：**
1. **脚本必须一起搬进宿主仓**。只搬 C# 命令壳、脚本留在 Diana，失效域没变，等于没做。
2. **必须放在宿主的非冻结层**（`Extensibility` 是现成先例：「演进层，不受宿主冻结门禁约束」）。
   否则"宿主改动谨慎"会变成"路线改不动"。冻结的是契约，不是路线。
3. **补一个离线开关** `--install-module <path>`（照 `--repair-autostart` 的样子）：
   宿主服务起不来时也能装包。这格不填，恢复矩阵还缺一角。

**不搬的那一半**：`docs.*` / `kit.*` / `relay.*` / `project.*` 留在 Diana，
Diana 变成"知识与工具"模块，继续可热重载。

**形态见下面「开发路线的暴露面：只走 CLI」。** 第 4 步我上一轮写的
「命令面跟着搬」是错的，已改：命令面**不搬，直接退役**，能力变成 CLI 子命令。

**这件事整体排在「宿主还能拆什么」的 A、B 之后**——先知道宿主该留什么，
再决定往里加什么，否则搬进来的东西会和一堆待删的旧代码搅在一起。

## 度量要换一个

- MCP 是纯托管、无 WPF、无原生锁 → 搬出去是**真**可热替换，性价比最高
- 前端那些搬出去了也换不掉 → 账面小了，可替换比例没变

# 开发路线的暴露面：只走 CLI（2026-08-21 定）

**仍然走命令总线，但交互只经命令行；不暴露为 Web，也不投影进 MCP。**

这一条同时解决了「谁是权威」：**一个实现（总线命令），一个门（CLI）**。
不是「CLI 一套 + 总线一套」，那样会漂移。

## 为什么 CLI 是对的家

这条原则本仓自己写过，在 `App/Program.cs:11`：

> 为什么不复用 `vulcan.command.manual`：那条命令带本地二次确认闸口，无人值守的
> 发布管线跑不了……**命令手册是发布产物而非运行时操作，用显式的 CLI 入口更诚实。**

开发路线整个是构建期，不是运行时操作。现成先例两个：
`--export-command-manual`、`--repair-autostart`。

## 关键事实：整条路线里只有两步真的需要活进程

| 步骤 | 需要活着的服务吗 |
|---|---|
| 开工作区 / 列 / 合并 / 回收 | 否，git + 文件 |
| 门禁、构建、打包、促级 | 否，dotnet + ps + 文件 |
| 装进运行区 | **否——拷文件就行** |
| 重载 | **否——`EnableFileWatching` 默认 true，`ModuleDirectoryWatcher` 直接挂 `Reload`** |
| 解锁被占用的 DLL | 是（纯托管可卸载的模块不需要） |
| 观察装载结果 | 是（有文件回退：读日志） |

实测：往模块槽拷完文件，宿主自己就重载了，一次 `vulcan.module.reload` 都没调。

## 两半的暴露面不一样，别搞混

- **构建期命令**（worktree / release / gate / promote）→ **CLI 独占**，
  不进 MCP 投影，`/api/command` 也拒绝。
- **运行期命令**（`module.install/reload/unload/list`）→ **保持 MCP + Web 可见**。
  它们是恢复路径（见第 1 项），恰恰要在所有模块都坏掉时还能被 agent 调到。

落地手段：`McpExposurePolicy` 硬排除 + WebGateway 拒绝；
`Core/Commands/CommandExecutionSite.cs` 已经有这个概念的位置，加一个站点值即可。

## 界面还想驱动一轮开发的话

允许总线上留**不含任何逻辑的中继**（一行 shell out），比如 Janus 的分支图谱页。
有逻辑的中继就是第二个实现，会漂移——那是这条决议要防的东西。

顺带说破一件事：**Diana 今天的命令本来就是薄壳**——
`DianaReleaseCommands.cs:216` 注释写着「必须用嵌套的 powershell.exe 调起管线」，
它 spawn 一个 detached PowerShell 去跑那 1504 行。真正的实现一直在脚本里。
这个提案等于把那个脚本提升为宿主里的一等 CLI，然后谁都能调。

## 动手时必须顺带修的地雷

`Program.Main` 现在的形状是：**不认识的参数静默忽略，然后起服务**。
上一轮「冷启动开出第二个宿主」就是这么来的。加子命令层的同时必须把未知参数
改成报错退出——否则 `HistoryVulcan.exe worktre create`（少打一个字母）
会**默默起一个新服务**。

## 还没定的一件事

子命令挂在 `HistoryVulcan.exe` 上，还是单独一个小 exe？
倾向前者：跟着它要修的东西一起发布，恢复矩阵最好；后者多一个要同步的产物。

# 待修清单（2026-08-21 迁移完成后记录，本轮不动）

## 一、两个弹窗问题——归一轮「确认框」专项

**1. `vulcan.app.quit` 的确认框会弹在看不见的地方。**

Aurora 主窗口最小化时，确认框跟着不可见，而退出指令就一直挂在那里等——
今天为此卡住两次，第二次排查用了进程 CPU 增量（增量为 0）加 EnumWindows 枚举
才确认是「两个『需要确认』窗口在等」，而不是死锁。

要修的不是 quit，是**确认框的呈现**：宿主进程在无人值守时被远程/脚本触发确认，
必须要么把窗口带到前台，要么超时失败，不能无限等一个没人看得见的框。

**2. `mcp.confirm=host` 实际不弹框。**

网关拿到的是硬接的「一律拒绝」实现，不读 `Bus.Confirmation`。因此即使 Aurora
已装载、能弹窗，远端危险指令仍然一律被拒——配置项的名字和行为对不上。

4.4.0 的迁移里**逐字保留了这个行为**，没有顺手修：改成读 `Bus.Confirmation`
会让远端危险指令**开始**能被人工放行，那是安全语义变更，不该混在一次搬家里。

两条同源：确认这件事在「无人值守的服务进程」里到底意味着什么，没有想清楚。
建议合成一轮做，先定语义再改代码。

## 二、`vulcan.log.source` 未知指令——单独一轮

控制台的日志来源筛选调用 `vulcan.log.source`，而实际注册的是 `aurora.log.source`。
昨天报了 92 次，今天最早 10:37，**与网关迁移无关**。
属于「界面搬进 Aurora 时改了域，调用点没跟上」的遗留，同类可能还有别的，
值得一轮把界面侧的指令名对一遍。
