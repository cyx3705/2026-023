# OneHistory 平台远期规划手册

日期：2026-11-07。状态：方向性规划，不是现行合同；行为仍以 `current/` 下合同为准。
来源：2026-11-07 用户与 Claude 的架构讨论（方案 1 / 方案 2、壳与宿主、平台价值评估）。

本手册回答三件事：这套平台要成为什么、哪些东西永远不动、接下来按什么顺序长。

## 一、定位：全局单实例、只服务一个人

OneHistory 不是多人复用服务，是**以个人为中心的私人软件平台**。

目标形态：**用户名下的所有机器组成一个逻辑宿主，全网只有一个系统实例。** 每个模块在逻辑宿主内只有一个归属；用户在任何一台电脑或手机上打开，看到的都是同一个系统，调用者不需要知道指令在哪台机器执行。

这与常见方案都不同：

- 去中心化方案默认多人，要处理信任、共识、权限隔离；
- 个人云方案默认有一台中心服务器；
- 本平台是「多台机器逻辑上是同一个宿主」，信任边界就是一个人。

宿主源码里已有 `LogicalHostId`、模块归属账本、节点 TLS 直连与包分发（V8.0 首期），方向早已确定；缺的是真实多机日常使用。

## 二、现状盘点（2026-11-07）

HistoryClio 各仓代码行（排除 obj/bin/发布目录）与 2026-09 以来提交数：

| 类别 | 仓 | 代码行 | 9 月以来提交 |
| --- | --- | --- | --- |
| 平台层 | Vulcan 23.0k、Janus 20.5k、Aurora 13.7k、Mercury 5.4k、Diana 4.4k | 约 67k | 298 |
| 直接产出价值 | Strenua 28.6k、Minerva 24.1k、Ratio 9.3k、Norma 2.4k、Usus 1.3k | 约 66k | 238 |

判断：

- **没烂。** 模块隔离清楚，6.0 起契约收窄为 `IModuleContext`，测试占比约 1/4～1/3，新模块 2～3k 行即可接入。
- **真正的价值核心**是「一切能力都是总线上的指令、自描述、经 MCP 暴露给 AI」——AI 能一句话驱动 SolidWorks 出图就靠它。
- **走偏的信号**：宿主两个多月 5.x→8.0；Aurora 数日内 WPF→Web→MAUI 壳→去边框→Mercury 唤起；为多人场景准备的机制（证书、归属账本、跨节点包分发）先于真实多机使用落地；大量 finish 未 push。

## 三、核心判断：腰细，而不是平台厚

用户的长期主义出发点是「平台搭得越厚，未来大翻篇的可能越小」。本手册修正为：

> **防止大翻篇的是一条极窄、极稳的中间层（窄腰），不是平台的厚度。** 平台越厚，能坏的面越多。

证据就在本仓历史：4.x→5.0 全体系一度不可用，根因是模块能碰到宿主内部类型（接触面大），不是平台太薄；6.0 把契约收成 `IModuleContext` 后才稳定。7.0（NuGet 包）、8.0（跨平台、两节点）若窄腰不动，本应都是宿主内部的事。

长寿系统（TCP/IP、Unix 管道）都是「中间极窄，两边随便换」。平台的长期投入应该是**把窄腰写死**，其余一切可替换。

## 四、窄腰不变量

以下四项构成窄腰。宿主、Aurora、壳、节点层怎么重写，只要这四项不变，模块、AI、网页都不用动。

| 不变量 | 内容 | 兼容规则 |
| --- | --- | --- |
| 指令文本 | `域.类.动作 参数=值` | 只增不改；改名须保留旧名转发 |
| 回执信封 | `success / message / data`，data 为 camelCase JSON | 字段只增不减 |
| 自描述 | 参数、只读、确认级别、示例 | 只增不减；`diana.docs.*` 读出 |
| 逻辑身份 | 逻辑宿主 GUID、模块名、归属节点 | 模块名稳定；归属可迁移 |

**主版本规则：只看窄腰动没动。** 窄腰不动，不准升主版本，不准要求模块重编。7.0/8.0 这类变更今后应落在次版本。

配套要求：

1. 为四项不变量写合同测试，变更即红。
2. **升级必须可退回**：新旧宿主并存，模块包按契约版本留档，一条命令退回上一版。系统任何时候都不能进入「全部不可用」——这是消除 4→5 那次焦虑的根本办法。（宿主现有自替换能否整体回滚，待核对。）

## 五、目标架构：Aurora 单实例（方案 1）

```
机器1        机器2        机器3
  │            │            │
vulcan ⇄ vulcan ⇄ vulcan        ← 控制面：节点直连，指令按归属路由
 │模块        │aurora 服务  │模块
              │模块
  ↓ 浏览器 / 壳访问同一个 aurora
机器1   机器2   机器3   手机
```

原则：**模块装在哪台机器，是因为它要控制那台机器的东西。** Aurora 不控制任何机器，只是网页服务，所以与其他模块一样只装一份，所有终端都连它。

对比曾讨论的方案 2（每台机器一个 aurora，即 V8-DES-009「每台电脑一个前端」）：

| | 方案 1：单一 aurora | 方案 2：每台 aurora |
| --- | --- | --- |
| 宿主 | 前端特例可全部删除，更扁平 | 需要 FrontendRole 特例贯穿节点层 |
| 本机能力 | 须外迁到所在机器的模块 | 天然在本机 |
| 单点 | aurora 所在机器离线则无界面；可经归属账本换机 | 各机独立 |
| 推送目标 | 一个通道看到所有终端，按发起方挑 | 同样要按发起方挑 |

**决定：采用方案 1。** 本手册取代 V8.0 升级书 V8-DES-009 的「前端按节点定位」方向；V8-DES-009 中「确认回到发起操作的界面」「确认通道缺失时保留拒绝闸口」两条保留。

### 5.1 删除宿主前端特例

Aurora 变为普通单归属模块后，节点层下列特例可删除：`CanLoad` 中 FrontendRole 直接放行、`IsLocal` / `ReceiveEvent` / `ExecuteRemoteAsync` 中的 `FrontendOwner` 判断、`_frontends` 与 `node:frontend` 前端转发通道、`NodeCommandCall.Frontend` 分支。其他模块调 `aurora.ui.*` 与调任何远程指令一样走 `NodeRoute`。

### 5.2 Aurora 本机职责外迁清单

| 现在在 Aurora | 控制的是 | 迁往 |
| --- | --- | --- |
| Web `/api/files` 浏览本机磁盘（选文件/目录） | 某台机器的文件系统 | 那台机器上的指令（如 Diana 文件列举），网页调用时指定目标节点 |
| `ShellLauncher` 拉起壳、`AllowSetForegroundWindow` | 本机进程与前台窗口 | Mercury（每台机器的唤起本来归它）或壳自身 |
| `WebFrontend` 无网页时开系统浏览器 | 本机进程 | Mercury |
| `AuroraService` 为 Minerva 等保留的 STA 线程 | 本机 WPF 窗口 | 宿主或需要窗口的模块自身 |

外迁后 Aurora 只剩「网页 + 推送 + 读自己的数据目录」。此项单机即成立，不依赖多机。

### 5.3 推送按发起方路由

`FrontendChannel.PickTarget` 现按「最近活跃网页」挑选。方案 1 下同一通道同时连着多台机器的壳、浏览器与手机，界面指令（确认框、刷新）须回到**发起这次操作的会话**：指令携带会话来源，无来源时才退回最近活跃。

## 六、壳与宿主：进程分开，安装合并

在电脑上壳与宿主都是「每台常驻一份的本机进程」，看起来重叠；但角色不同：宿主 = 这台机器可被控制，壳 = 这台机器可看界面。

| 机器类型 | 宿主 | 壳 |
| --- | --- | --- |
| 办公电脑 | 要 | 要 |
| 手机 | 装不了（宿主为 `net8.0-windows`） | 要 |
| 只干活的机器 | 要 | 不要 |

不合并进程的理由：平台不同（宿主 net8.0-windows，壳 net9.0 MAUI）；节奏相反（宿主常发版并自替换，壳要越薄越少更新）；崩溃隔离（WebView 崩溃不能带走宿主）。

**合并安装**：壳 Windows 版作为宿主经节点包分发（`PackageArtifactStore`）下发的制品，由 Mercury 负责拉起与唤回。迁移一台电脑 = 只装宿主 → 加入节点 → 自动获得 Mercury 与壳。手机只装 apk，作为纯遥控器。壳继续保持「不引用宿主」的合同测试。

## 七、演进路线

按顺序推进；每一阶段完成后系统都可日常使用。

| 阶段 | 内容 | 依赖多机 |
| --- | --- | --- |
| 0 保险 | 推送全部 finish 未 push 的提交 | 否 |
| 1 守腰 | 写窄腰不变量合同测试；宿主升级可整体回退 | 否 |
| 2 Aurora 瘦身 | 完成 5.2 外迁清单 | 否 |
| 3 去特例 | 完成 5.1，Aurora 成为普通单归属模块 | 否 |
| 4 端到端切片 | 第二台机器装宿主并配对 → Norma 归属到那台 → 在本机网页调用 → 手机打开看到同一系统 | 是 |
| 5 向外长 | 由真实使用拉动：节点层多对端、壳随宿主分发、归属迁移体验 | 是 |

阶段 4 只做跑通链路的最小集：节点层支持第二个对端、Portunus 远程鉴权后放开 Kestrel 局域网监听（Program.cs「REQ-WEB-001 等 Portunus 远程认证」）、推送按发起方路由。

## 八、防漩涡守则

1. **不在没有真实使用的地方加厚。** 新的平台机制须由一个正在日常发生的场景拉动；否则记入本手册「未决」，不实施。
2. **主版本只为窄腰。** 见第四节。
3. **先切片，后铺满。** 新能力先打通一条端到端链路，再扩展广度。
4. **业务模块优先。** 平台阶段之间，精力回到 Strenua、Minerva、Norma/Usus 等直接产出价值的模块。
5. **永远可退回。** 任何升级前确认退路存在。

## 九、未决问题

- 宿主现有自替换能否整体回滚到上一版（阶段 1 前核对）。
- Aurora 所在机器离线时，是否需要「只读降级页」或手动换归属的快捷入口。
- 会话来源如何进入指令（窄腰扩展字段 vs 节点层上下文），须保证不破坏指令文本不变量。
- 壳随宿主分发后的更新策略：跟随宿主，还是只在窗口桥协议变化时更新。
