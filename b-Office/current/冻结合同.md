# HistoryVulcan Core 冻结合同

> 生效版本：**3.9.0**　立约日期：**2026-08-11**
>
> 本文是 `HistoryVulcan.Core` 公开面的稳定性承诺。冻结的是**契约**，不是代码——
> Core 的内部实现可以随时重构，承诺的是消费方看得见的那一面不变。

## 1. 为什么要有这份合同

冻结之前，改 Vulcan 是一件昂贵的事：Core 的公开面里混着大量只服务于单一模块的类型，
于是模块的正常演进被迫触发宿主的版本事件，而宿主的稳定诉求又让模块每次改动都要走
完整门禁。两头都坏。

八个版本的公开面增量显示，推动 Core 增长的从来不是地基本身：

| 来源 | 累计推动 Core | 实质 |
| --- | --- | --- |
| `Core.CommandSurface` | 79 行 | 控制台命令目录（单一模块消费） |
| 全局快捷键 `Core.Input` | 46 行 | 「按键 → 命令名」，载荷本就是命令 |
| 声明式面板 `Core.Panels` | 38 行 | 注定生长的数据 schema，零模块消费 |
| 命令工作台 `Core.Modules` | 15 行 | 单一模块的挂载点 |

这些已全部清出。Core 已发布面从 512 行降到 362 行，减少 29%，**且没有任何例外条款**。

## 2. 冻结范围

| 程序集 | 承诺 | 门禁 |
| --- | --- | --- |
| **HistoryVulcan.Core** | **冻结承诺已于 4.0 解除**（DEC-049）。公开面可演进；删除走主版本并进消费变更摘要 | 公开 API 基线 + 质量门禁 |
| HistoryVulcan.Services | 稳定，随宿主实现演进 | 公开 API 基线 |
| HistoryVulcan.ServiceHost | 稳定，随宿主实现演进 | 公开 API 基线 |

5.0 起不再有 `HistoryVulcan.Extensibility`。能用命令名表达的联动走命令总线；活对象走 `CommandResult` 载荷，由认领方解释。

## 3. Core 里现在有什么

| 命名空间 | 内容 | 为什么冻得住 |
| --- | --- | --- |
| `Commands` | 总线、注册表、描述符、上下文、结果、解析；`DomainFocus` / `CommandClassLabels` | 全体模块的集成面 |
| `Modules` | `ModuleInfoBase`、`IModuleContext`（仅 Bus + RegisterCommands）、`IModuleContextAware`、`IDeferredStartupWork` | 注册器与指令暂存 |
| `Logging` / `Storage` | 日志与设置契约（供宿主与开发总线，不注入模块） | 宿主内部消费 |

5.0 已删除 `Clients`（`ClientKind` / `ClientSession`，会话身份由 Portunus 自持）与 `Mcp`（远端可见性走总线上的 `HiddenReason` / `Level` / `Readonly`）。

5.0 起本节由 DEC-052 替代：宿主不再冻结 MCP 安全面或客户端会话类型。远端可见性看总线标志；会话身份由 Portunus 自持。

## 4. 什么情况下允许动 Core

冻结不是"永不修改"，而是"修改需要理由，且理由要写下来"。允许的情形只有三类：

1. **安全缺陷修复**——包括审计、确认、暴露策略的漏洞。
2. **正确性缺陷修复**——公开面语义与文档不符，且文档是对的。
3. **新增全体模块都需要、且不属于任何单一消费方的能力**——需同时满足下述判据。

### 新增判据（必须全部满足）

- **至少两个模块需要它**，且一年后仍然成立；
- **无法用命令名表达**——凡是能走命令总线的联动，一律走命令总线（见 `CommandBus.InvokeAsync`）；
- **不是任何单一消费方的展示、协议或便利功能**。

任何一条不满足，它就不该进 Core：用命令名表达，或由认领该命令的模块解释载荷。

### 明令禁止

**不得再向 `CommandDescriptor` 增加字段。** 本类历史上为每个消费方各长过一个字段
（`Domain`/`CommandClass` 用于目录展示、`AllowMcpExecution` 用于 MCP、`ExecutionSite`
用于前端路由、`SupportsUndo` 是从未实现的预留位）。后两个已经删掉——`SupportsUndo`
接线至今零行为，`ExecutionSite` 在界面变成宿主内模块后全仓无人置为 `Frontend`，
它的四个读取点都是永远走不到的分支。

4.8.0 又收掉一组：`Dangerous`、`ConfirmPrompt`、合成属性 `IsDangerous` 三个成员
表达的是同一件事——「执行前要不要问人」。三份表达意味着不同消费方各读各的
（MCP 读合成属性、总线读闸口、目录读元数据），于是同一条指令在不同的面上
可以给出不同答案。现在只剩两个：`Level` 是唯一权威，`ConfirmPrompt` 只提供文案。
两者不一致时注册表拒绝注册，因为「写了文案却没升级别」的后果是闸口静默消失，
那是最不该靠人记住的一类错误。

同一轮还收掉了 `AllowMcpExecution` 与 `AllowCliExecution`：那是「给每个消费面各发一个
令牌」，而**暴露与否只该有一处声明**。现在是 `HiddenReason`——写原因即隐藏，不写即暴露，
理由本身就是唯一能让后来人判断该不该继续隐藏的东西。它同时取代了 `McpExposurePolicy`
里那份按名字写的硬排除名单：那份名单失效过四次，每次都是指令改了名而规则还盯着旧名字。

至此描述符上的声明位是四个：`Readonly`（改不改东西）、`Level`（问不问人）、
`ConfirmPrompt`（问的时候说什么）、`HiddenReason`（暴不暴露）。

新的消费方能力一律走 `CommandDescriptor.Annotations`，键为 `<消费方>.<能力>`，
例如 `mcp.execute`、`catalog.hidden`。总线只负责原样携带，消费方自行定义与解释自己的键。

这条规则是整份合同能长期成立的关键：清理存量只解决一次，堵住增量才解决长期。

## 5. 变更流程

1. 对照第 4 节判据自查；不满足即改投演进层。
2. 满足则升版本，在 `b-Code-Eng/public-api-baselines/<版本>/` 建立批准基线。
3. 已发布面的移除或签名变更必须以 `*REMOVED*` 显式声明，不得静默删除。
4. 走完整发布管线（`vulcan.release.cycle`）：宿主合同、单元测试、质量门禁、
   公开 API 基线四道门禁全过方可发布。
5. 破坏性变更须在本文件追加记录，写明原因与消费方迁移路径。

## 6. 给未来的自己

半年后你会看到两个程序集，并且很可能忘记为什么。原因只有一条：

> **稳定性承诺决定归属，功能领域不决定归属。**

同样是"命令"相关的东西，`CommandBus` 在 Core 而 `DomainFocus` 在演进层；同样是 MCP
相关的东西，审计铁律在 Core 而工具 schema 在演进层。判据始终是那一个问题——
**它会不会因为某个消费方的需要而改变？**

会，就不属于 Core。

## 7. 冻结前的最后清理记录

以下都属于"现在不做就永远做不了"，已于 3.8.0–3.9.0 完成：

- **删除 `CommandDescriptor.SupportsUndo`**——「Q6 预留、首版不实现」，接线至今零行为。
  冻结一个从未被验证过的预留位，等于承诺一个自己都不知道对不对的形状。
- **`ClientSession`/`ClientKind` 由 `Core.Mcp` 正名为 `Core.Clients`**——它并非 MCP 协议
  形态。名字要说实话，而冻结之后命名空间就再也改不了了。
- **`CommandDescriptor` 开注解槽**——见第 4 节。

## 8. 5.x 冻结前置：四步

> 记于 **5.1.0**（2026-08-24），冻结前审查之后。
> `freezeTag` 至今仍是 `v3.0.3`——**5.x 从未声明过冻结**。

本节取代 `模块边界整治备忘.md` 与 `宿主轻量化报告.md`（已迁入 `history/`）：
那两份分别写于 4.6 与 4.8，各自的结论已被 5.0 的重构与 5.1.0 的审查覆盖或推翻。
留着两份过期地图比没有地图更坏。

### 现状（5.1.0 实测）

宿主 10 633 行：Core 2047（仅 `Commands`/`Modules`/`Logging`/`Storage` 四个目录）、
Services 7018、ServiceHost 1489、App 79。118 个测试通过，质量门禁与公开 API
冻结门禁均通过。冻结后的净公开面：

| 程序集 | 已定版 | 新增 | 移除 | 冻结后 |
| --- | ---: | ---: | ---: | ---: |
| HistoryVulcan.Core | 282 | 22 | 213 | **237** |
| HistoryVulcan.Services | 208 | 102 | 213 | **234** |
| HistoryVulcan.ServiceHost | 57 | 29 | 7 | **79** |

### 第一步：清账（不依赖任何决策，可立即做）

`*REMOVED*` 条目里 **Core 有 146 条、Services 有 137 条对不上任何已定版条目**——
它们移除的是从未定版过的东西，是几轮重构里「加了又删」留下的账。

不清就冻结，等于把一本乱账封存起来。清完 Unshipped 应只剩真正的净增
（Core 22 / Services 102 / ServiceHost 29）。

### 第二步：契约必须先被验证过（硬前提，不在宿主侧）

**截至 5.1.0，没有一个模块真正接上宿主。** Portunus / Minerva / Diana 的 `Attach`
抛 `MissingMethodException`（调用了 5.0 删除的 `IModuleContext.Settings` 与
`DataDirectory`），Diana / Mercury 注册 0 条指令，Janus 只剩 1 条，指令面从 167 掉到 77。

冻结的意思是「这套契约以后不再改」。而**这套契约目前还没有一个模块成功消费过**。
在六个模块都对着 5.x 跑通之前冻结，等于宣布一份从未被验证的契约永久生效。

宿主侧该做的已经做完：5.1.0 起 `Attach` 失败不再被报成 ✓，
`vulcan.module.list` 直接列出未接上的模块与原因。剩下的是模块自己来适配——
**宿主不为模块提供抽象，也不为让模块跑通而回退契约。**

### 第三步：两个设计决策（冻结会把它们焊死）

**其一，宿主自替换走哪条路。** `vulcan.release.cycle name=HistoryVulcan` 在服务运行时
会撞上 `z-Publish/host/HistoryVulcan.exe` 的文件锁。现有行为是失败并回滚（安全），
但没有前置检查。停服、影子目录、还是独立重启器——这决定
`HostSnapshotBuilder` 与 `PublishLayout` 的形状。

**其二，发布管线 3500 行要不要留在宿主里。** `Services/Development/` 占宿主三分之一。
`宿主轻量化报告` 曾建议移出成 pinned 模块，但同一份报告也点破了可能推翻它的问题：
pinned 装进 `AssemblyLoadContext.Default` 不可卸载，**宿主自身升级时它也换不掉**。

这两件是同一个问题的两面，必须一起定。冻结前不定，就是把当前形状永久留下。

### 归档时提炼出的唯一未结项

`模块边界整治备忘` 的待办里，只有一条到 5.1.0 仍然成立：

- **`vulcan.command.manual` 还在宿主**（`Services/Commands/CommandCatalogCommands.cs`）。
  备忘当初判定它该归 Diana——生成手册是发布期的事，不是总线的事。
  冻结会把它连同 `vulcan.command.*` 一起锁进宿主的指令面，之后再迁就是破冻。

其余待办均已落地或被后续设计推翻，不再列入现行路线：
未知参数静默起服务（已修，`HostAction.Error`）、
`vulcan.app.show/hide/close/focusconsole` 迁 Aurora（已完成，宿主只剩 `vulcan.app.quit`）、
控制台拆分（已完成，宿主已无 `ConsoleView`）、MCP 变模块（已完成，HistoryPortunus）、
UI 生命周期收口（5.0 删除 `IUiModule` 整套）、
给 `vulcan.module.install` 开 MCP（已被推翻——它现在声明 `HiddenReason` 硬排除，
换宿主的包不该交给远端）。

### 第四步：声明冻结（机械劳动，需授权）

把 Unshipped 并进 Shipped、`module-publish.manifest.json` 与 `project.manifest.json`
的 `freezeTag` 从 `v3.0.3` 升到 5.x、打标签、写冻结执行证据进 `history/`。

### 顺序说明

第一步随时可做。**第二、三步不是工作量问题，是顺序问题**——
契约没被任何模块验证过就冻结，管线归属没定就冻结，这两件事冻完都得破冻才能改。
