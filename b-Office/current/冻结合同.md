# HistoryVulcan 宿主冻结合同

> 当前生效版本：**5.1.2**　冻结标签名：**`v5.1.2`**　重新冻结日期：**2026-08-31**
>
> 本文是 HistoryVulcan 宿主公开面与模块接入面的稳定性承诺。冻结的是**契约**，不是代码——
> 内部实现可以重构，消费方看得见的注册器、命令总线、开发/发布总线与公开 API 必须守住。

## 1. 为什么要有这份合同

冻结之前，改 Vulcan 是一件昂贵的事：Core 的公开面里混着大量只服务于单一模块的类型，
于是模块的正常演进被迫触发宿主的版本事件，而宿主的稳定诉求又让模块每次改动都要走
完整门禁。两头都坏。

八个版本的公开面增量显示，推动 Core 增长的从来不是地基本身：

| 来源 | 累计推动 Core | 实质 |
| --- | --- | --- |
| `Core.CommandSurface` | 79 行 | 控制台命令目录（单一模块消费） |
| 全局快捷键 `Core.Input` | 46 行 | 「按键 → 命令名」，载荷本就是命令 |
| 声明式面板 `Core.Panels` | 38 行 | 注定生长的数据 schema，零模块消费 |
| 命令工作台 `Core.Modules` | 15 行 | 单一模块的挂载点 |

这些已全部清出。Core 已发布面从 512 行降到 362 行，减少 29%，**且没有任何例外条款**。

## 3. Core 里现在有什么

| 命名空间 | 内容 | 为什么冻得住 |
| --- | --- | --- |
| `Commands` | 总线、注册表、描述符、上下文、结果、解析；`DomainFocus` / `CommandClassLabels` | 全体模块的集成面 |

5.0 起本节由 DEC-052 替代：宿主不再冻结 MCP 安全面或客户端会话类型。远端可见性看总线标志；会话身份由 Portunus 自持。

## 4. 什么情况下允许动宿主冻结面

冻结不是"永不修改"，而是"修改需要理由，且理由要写下来"。允许的情形只有三类：

1. **安全缺陷修复**——包括审计、确认、暴露策略的漏洞。
2. **正确性缺陷修复**——公开面语义与文档不符，且文档是对的。
3. **新增全体模块都需要、且不属于任何单一消费方的能力**——需同时满足下述判据。

### 新增判据（必须全部满足）

- **至少两个模块需要它**，且一年后仍然成立；
- **无法用命令名表达**——凡是能走命令总线的联动，一律走命令总线（见 `CommandBus.InvokeAsync`）；
- **不是任何单一消费方的展示、协议或便利功能**。

任何一条不满足，它就不该进 Core：用命令名表达，或由认领该命令的模块解释载荷。

### 明令禁止

**不得再向 `CommandDescriptor` 增加字段。** 本类历史上为每个消费方各长过一个字段
（`Domain`/`CommandClass` 用于目录展示、`AllowMcpExecution` 用于 MCP、`ExecutionSite`
用于前端路由、`SupportsUndo` 是从未实现的预留位）。后两个已经删掉——`SupportsUndo`
接线至今零行为，`ExecutionSite` 在界面变成宿主内模块后全仓无人置为 `Frontend`，
它的四个读取点都是永远走不到的分支。

4.8.0 又收掉一组：`Dangerous`、`ConfirmPrompt`、合成属性 `IsDangerous` 三个成员
表达的是同一件事——「执行前要不要问人」。三份表达意味着不同消费方各读各的
（MCP 读合成属性、总线读闸口、目录读元数据），于是同一条指令在不同的面上
可以给出不同答案。现在只剩两个：`Level` 是唯一权威，`ConfirmPrompt` 只提供文案。
两者不一致时注册表拒绝注册，因为「写了文案却没升级别」的后果是闸口静默消失，
那是最不该靠人记住的一类错误。

同一轮还收掉了 `AllowMcpExecution` 与 `AllowCliExecution`：那是「给每个消费面各发一个
令牌」，而**暴露与否只该有一处声明**。现在是 `HiddenReason`——写原因即隐藏，不写即暴露，
理由本身就是唯一能让后来人判断该不该继续隐藏的东西。它同时取代了 `McpExposurePolicy`
里那份按名字写的硬排除名单：那份名单失效过四次，每次都是指令改了名而规则还盯着旧名字。

至此描述符上的声明位是四个：`Readonly`（改不改东西）、`Level`（问不问人）、
`ConfirmPrompt`（问的时候说什么）、`HiddenReason`（暴不暴露）。

新的消费方能力一律走 `CommandDescriptor.Annotations`，键为 `<消费方>.<能力>`，
例如 `mcp.execute`、`catalog.hidden`。总线只负责原样携带，消费方自行定义与解释自己的键。

这条规则是整份合同能长期成立的关键：清理存量只解决一次，堵住增量才解决长期。

## 5. 变更流程

1. 对照第 4 节判据自查；不满足即改投演进层。
2. 满足则升版本，在 `b-Code-Eng/public-api-baselines/<版本>/` 建立批准基线。
3. 已发布面的移除或签名变更必须以 `*REMOVED*` 显式声明，不得静默删除。
4. 走完整发布管线（`vulcan.release.cycle`）：宿主合同、单元测试、质量门禁、
   公开 API 基线四道门禁全过方可发布。
5. 破坏性变更须在本文件追加记录，写明原因与消费方迁移路径。

## 6. 给未来的自己

半年后你会看到两个程序集，并且很可能忘记为什么。原因只有一条：

> **稳定性承诺决定归属，功能领域不决定归属。**

同样是"命令"相关的东西，`CommandBus` 在 Core 而 `DomainFocus` 在演进层；同样是 MCP
相关的东西，审计铁律在 Core 而工具 schema 在演进层。判据始终是那一个问题——
**它会不会因为某个消费方的需要而改变？**

会，就不属于 Core。

### 第二步：通用模块契约已验证　✅ 已完成（2026-08-31，5.1.2）

历史上曾出现模块调用已删除的上下文成员、注册指令为空或部分注册的情况。

宿主不为模块提供领域抽象，也不为让某个模块跑通而回退已冻结契约。

## 9. 5.1.3 在不动冻结面的前提下修接入次序（DEC-057）

> 源码线推进到 **5.1.3**；冻结标签仍为 **`v5.1.2`**，三份 Shipped 一个符号未动。

### 为什么这条改动没有破冻结

第 4 节允许动冻结面的第二类情形是「正确性缺陷修复——公开面语义与文档不符，且文档是对的」。
本轮修的正是这一类：接入面承诺模块 `Attach` 时能用命令总线与其它模块集成，而实现里
**所有模块指令要等整轮装载结束才一次性登记**，于是 `Attach` 期间的跨模块调用必然落空，
落空多少还取决于剩余模块的装载耗时。

修法没有向 Core 增加任何公开面：新增能力全部用命令名表达
（`vulcan.module.ready` 查就绪，`<域>.host.ready` 收通知），
这正是第 4 节「能用命令名表达的联动，一律走命令总线」要求的形态。
`dependsOn` 与 `ui` / `pinned` 同一模式由宿主直读 manifest，不改已定版的
`ModuleDiscoveryEntry` 构造函数。

### 改了什么

| 面 | 5.1.2 | 5.1.3 |
| --- | --- | --- |
| 装载次序 | 名称序 | manifest `dependsOn` 排定的拓扑序；无声明时仍是名称序 |
| `Attach` 时机 | 扫描期，指令尚未登记 | 快照提交后，按次序逐个；接一个登记一个 |
| 完成点 | 只有一行日志 | `ModuleHost.IsReady` + `vulcan.module.ready` + `<域>.host.ready` 通知 |
| 公开 API | — | 无变化（新增成员均为 internal） |

### 冻结面账目

| 程序集 | 5.1.3 Shipped | 5.1.3 Unshipped |
| --- | ---: | ---: |
| HistoryVulcan.Core | 237（未动） | 仅 `#nullable enable` |
| HistoryVulcan.Services | 239（未动） | 仅 `#nullable enable` |
| HistoryVulcan.ServiceHost | 122（未动） | 仅 `#nullable enable` |

`b-Code-Eng/public-api-baselines/5.1.3/` 是本版批准基线，内容与 5.1.2 一致——
没有新增，也没有移除。

### 标签暂缓：等前后端一起测过再动

**在宿主 5.1.3 与 HistoryAurora 1.17.0 完成真机联调之前，不要动冻结标签。** 具体是：
不创建 `v5.1.3`，不把 `project.manifest.json` 或 `b-Code-Eng/pipeline/module-publish.manifest.json`
的 `freezeTag` 从 `v5.1.2` 改走。

理由是这轮改的是**接入面的时序**，而时序只有在真机上跑起来才算验过：单元测试能证明次序对、
就绪信号发得出，证明不了「界面在真实装载耗时下确实收到了通知、页面确实齐了」。
标签是给消费方的稳定性承诺，承诺不该建立在没跑过的时序上。

联调判据见验证合同「5.1.3 Startup Order Checks」的真机一节。通过之后再单独授权打标签。

| Core | `CommandRegistry.LegacyMethod` | 与 `GetMethod` 逐字相同，并入后者 |

| Core | `DomainFocus.WouldPrefix` | 把 `Resolve` 的判定抄了一遍；`Resolve` 的返回值与输入是否相等就是答案 |
| Services | `ModuleHost.FindModuleDomainConflicts` | 自 3.2.1 起就注明「装载路径不再调用」，此后无人调用 |

### 判定「死」的方式必须留档

不是读代码猜的。三处逐一核对：宿主源码、测试工程，以及运行区模块目录下**七个已部署模块的
二进制**（按元数据里的符号名比对）。按符号名比对时要按串尾定界——`set_ShouldUseRemote`
是 `set_ShouldUseRemoteCommand` 的前缀，不定界会把「没人用」误判成「有人用」。

**这套核对方式应当成为此后每次删除公开面的前置条件。** 冻结之后再想删，代价只会更高；
而「没人用」这句话如果不带核对方式，下一个读到它的人无从复查。

### 与第 5 节「走主版本号」的偏离

第 5 节要求删除走主版本号。本轮走 5.2，偏离已在 DEC-058 记明：十条的实测消费方为零，
破坏面为空。**下一轮若再有删除且消费方非空，必须走主版本号，不得援引本轮为先例。**
