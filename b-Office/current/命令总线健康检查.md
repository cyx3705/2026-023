# HistoryVulcan 命令总线健康检查

检查日期：2026-08-11  
适用版本：3.5.0 源码线  
关联需求：REQ-CMD-001、REQ-SVC-001、REQ-MCP-001、REQ-MCP-002

## 结论

本轮出现的“模块工具缺失”和 HTTP 429 都发生在 `CommandBus.ExecuteAsync` 之前，不是命令处理器随机失败：

1. 独立宿主原先把 `McpGateway` 装在前端，MCP 枚举前端局部注册表；非 UI 模块注册在后台权威表，
   所以只剩约 14 条 `vulcan_*`，模块命令没有进入工具面。
2. Web 网关把已经认证的本机 Shell 与公网 Web 客户端放在同一个每会话限流模型里。Shell 的目录、模块刷新、
   健康检查和用户命令共享一个会话；达到默认 120 次/分钟后，请求在进入总线前直接返回 HTTP 429。

修复后，独立宿主的 MCP、非 UI 模块和命令权威表统一归后台；本机 `loopback-shell` 控制通道不再消耗
公网配额，普通 Web/远端会话与失败鉴权限流保持不变。当前判断为：**Vulcan 核心总线和跨进程接入层健康，
但当前正式 Minerva 模块的 Worker 运行时路径存在部署阻塞；高并发执行背压仍是明确残余风险。**

## 实际链路

```text
前端 UI/控制台
  -> 前端 CommandBus（判断执行站点）
  -> ShellServiceClient /api/command
  -> WebGateway（鉴权、限流、权限）
  -> 后台 CommandBus
  -> 后台 CommandRegistry
  -> Vulcan 或模块处理器

MCP 客户端
  -> 后台 McpGateway（协议、策略、确认、审计）
  -> 同一个后台 CommandBus / CommandRegistry
  -> Vulcan 或模块处理器
```

模块热重载直接增删后台注册表。MCP 的 `tools/list` 与 `tools/call` 动态读取这张表，不保存模块名单或
工具数量常量，因此无需重启网关。

## 根因与修复

### MCP 只暴露 Vulcan

根因是“监听实例”和“命令权威表”分属不同进程。前端启用 MCP 只能看到 Shell 自己注册的框架/UI 命令；
后台虽已装载模块，但没有 MCP 读取它的注册表。

修复为后台创建治理存储、审计器与 `McpGateway`，注册完整 `McpCommands`，并在监听 Web/MCP 前同步
完成首次模块装载。前端设置 `EnableMcp=false`，继续经远程总线管理后台，不再占端口或维护第二份治理状态。

### HTTP 429

`WebGateway` 的默认 `web.ratelimit=120` 原本对每个认证会话一视同仁。本机 Shell 会话既是控制面又承载
用户命令，流量组合后会触达阈值。429 在鉴权之后、命令总线之前返回，因此日志表现为“服务命令请求失败”，
容易被误认为命令处理器不稳定。

修复只豁免同时满足 `ClientKind.Shell`、loopback 地址和 `AuthSubject=loopback-shell` 的已认证会话。
该会话在修复前已经具有本机 admin 权限，所以没有扩大既有信任边界。普通 Web、远端设备、配对和失败鉴权
仍执行原有限流。

## 残余风险

1. `CommandBus` 不提供全局并发上限或处理器队列。多个已授权客户端可并发进入线程安全由模块自行保证的
   非 UI 处理器；当前公网限流和 MCP 会话边界能削峰，但不是完整背压。后续若出现实际并发饱和，应新增按
   会话与命令类别的执行配额，不应重新限制本机控制通道的基础请求。
2. `McpExposurePolicy` 的模块解析器仍是进程级静态装配点，只支持一个权威 `ModuleHost`。这符合当前独立
   后台单宿主模型，但不支持同进程多租户。
3. 前端 WebSocket 只在连接时发布 UI 命令目录；运行期新增前端命令仍需重连。后台模块命令不受此限制。
