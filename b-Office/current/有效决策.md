# HistoryVulcan 有效决策

## DEC-049 前端整体切出，宿主无头化并解冻走 V4.0

- 状态：已接受
- 日期：2026-08-18
- 决策：`HistoryVulcan.Shell`（10,245 cs + 2,467 xaml = 12,712 行）与 `App` 的前端半边
  整体迁往 2026-026-HistoryAurora，产出独立应用 `HistoryAurora.exe`。
  `HistoryVulcan.exe` 变为无头服务：指令总线 + MCP + 模块托管 + 回环 IPC，工程不再 `UseWPF`。
- 决策：**解除 Core 自 3.9.0 起的公开面冻结**，本线走 **V4.0**。理由是模块契约要借这次收口
  （`IUiModule`、`IShellUiAware` 等界面契约最终会删除），继续维持冻结会让收口无法进行。
  解冻不等于随意改动：删除项必须逐条进消费变更摘要，并走主版本号。
- 决策：危险命令确认改为中继到 Aurora。宿主无头后不再有 `MessageBoxConfirmation` /
  `RemoteConfirmDialog`；Aurora 未连接时确认**拒绝**而非静默放行。
- 可行性依据（实测）：`Services` 与 `ServiceHost` 都不引用 `Shell`；服务进程只在
  `App.xaml.cs:301` 一处调用 `HistoryVulcan.Shell.Mcp.McpCommands.RegisterAll`。
  而 `Shell/Mcp/` 的 1,274 行里仅 `RemoteConfirmDialog.cs`（86 行）碰 WPF，其余 1,188 行
  是纯逻辑，迁入 `Services` 即可解开这唯一的结。
- 反面依据（实测）：曾尝试把前端命令改由模块注册，结果宿主强制改写域与来源，且模块命令只落
  服务进程、`DataDirectory` 语义随之改变。前端能力**无法**经模块路径承载，因此 Aurora 必须
  是应用而非模块。该次试验已回退。
- 施工方案：见 Aurora 仓 `b-Office/current/前端切出迁移方案.md`（REQ-A1..A4 / B1..B2 / C）。
- 前置阻塞：`z-Publish/host` 路径漂移必须先修，否则模块仓与 Aurora 都无法从干净状态构建。
- 替代条件：只有当界面被证明必须与服务同进程时，本决策才失效。

## DEC-047 两个本机网关共用传输层零件，但不合并监听器

- 状态：已接受
- 日期：2026-08-18
- 决策：把 `McpGateway` 与 `WebGateway` 之间逐字重复的 HttpListener 传输层零件
  （`ReadBearer`、`FixedEquals`、`TryClose`、按应用名派生端口、接受循环）收拢到
  `Services/LoopbackHttpTransport.cs`。两个网关**仍各自持有自己的监听器和端口**，
  生命周期互不影响。
- 不合并监听器的理由：合并只买到"少一个回环端口"，代价是 `vulcan.mcp.stop` 从"关闭端口"
  退化为"注销一条路由"——MCP 传输层将常驻在一个始终打开的监听器上。这与
  「MCP 与模块能力默认关闭、由消费方显式启用、不得恢复隐式监听」直接冲突，方向与缩小
  暴露面相反。两个网关的协议实现（JSON-RPC 会话与工具投影 vs 命令中继与 WS 事件流）本就
  不重叠，合并省不掉那部分；实测可去重的只有约 70–80 行，而这部分不合并也能去掉。
- 记录一次估算修正：合并收益先后被估为「300–500 行」与「150–250 行」，逐一比对后实际为
  70–80 行。后续若有人重提合并，应以本条实测为准，不要沿用早期估算。
- 连带改进：Web 网关的接受循环此前不捕获单次接受失败，一个坏连接会冒泡出循环并悄悄终结
  整条监听。改用共享实现后与 MCP 侧一致——记警告并继续。
- 替代条件：只有在 MCP 传输层不再需要独立启停（即「停掉 MCP 等于端口消失」不再是要守的
  性质）时，合并监听器才重新成为候选。

## DEC-046 本机 IPC 通道必须持券，回环不构成边界

- 状态：已接受
- 日期：2026-08-18
- 背景（实测）：在 3.12.1 运行中的宿主上，一个普通本地进程不带任何令牌，只加
  `X-HistoryVulcan-Client: Shell` 头 POST `/api/command`，即可在权威总线上执行命令（实测
  `vulcan.command.domains` 返回 HTTP 200）。该路径**没有任何 MCP 限制层**，因此 MCP 侧的硬排除
  ——`vulcan.app.quit`、`vulcan.module.install/remove`、全部 12 条 `vulcan.mcp.*`——在同机范围内
  可被整体绕过。MCP 自己的令牌还是可选的（未配置时完全不校验）。这是既有状况，不是 DEC-045 引入的。
- 决策：`WebGateway.Start` 用密码学随机数生成一枚 32 字节一次性凭据 `AccessToken`，`Stop` 时清空；
  `Authenticate` 要求回环、`ClientKind.Shell`、持本次凭据三者同时成立，缺一返回 401。凭据由
  `ServiceHost` 写入 `endpoint.json` 的 `accessToken` 字段，前端经既有的
  `ShellEndpointProfile.AccessTokenProvider` 携带。凭据不落设置、不可配置、不回显、不写日志。
- 原因：回环不是边界。前两个条件（回环、请求头）任何本机进程都能满足或伪造，只有凭据能区分
  "我们自己启动的前端"和"任意本机进程"。在合并网关之前必须先有这条真实边界，否则合并等于把一条
  文档上写着、实际不存在的边界固化进结构。
- 边界与残余风险：这条边界的实际强度等于 `%AppData%\HistoryVulcan\service\endpoint.json` 的读取
  权限。以当前用户身份运行的进程仍可读取该文件并取得凭据——这是本机同用户威胁模型下的固有上限，
  本决策不声称解决它。真正的收益是：**默认不再对任意本机进程敞开**，且宿主重启即换券。
- 连带修复（真机启动发现）：前端派生后台后的等待循环原先只判 `endpoint.json` 是否可读，
  而服务被强杀时来不及删除该文件，残留记录端口有效、`accessToken` 为空，循环第一轮即误判就绪，
  前端拿空凭据连新服务、稳定 401 后转本地模式（`/api/health` 显示 `shells=0`）。
  修法：连不上既有后台时先删除该记录再派生，等待条件改为「端口有效**且**凭据非空」
  （`App.IsUsableEndpoint`）；`AccessTokenProvider` 改为每次调用现读 `endpoint.json`
  而非捕获快照，使后台重启换券后前端能自行恢复。此缺陷在 3.13.0 前是潜伏的——端口恰好相同
  且后台不校验令牌，连上了就看不出来；补上凭据校验后它变成硬失败。
- 验收：`FreezeBlockerTests.GatewayAcceptsOnlyTheLoopbackShellSession` 覆盖伪造 Shell 头无券、
  持错券两种拒绝；`AccessTokenIsRegeneratedPerListenAndClearedOnStop` 覆盖每次监听换发与停止清空；
  `ServiceEndpointHandshakeTests` 覆盖残留/空券/无端口记录均不可用。
  真机冒烟：残留 endpoint.json 条件下启动，`/api/health` 须为 `shells=1`，
  无券请求 401、持券 200，重启后令牌改变。
- 替代条件：只有更强的本机进程身份验证（如命名管道 + 进程令牌校验）可以替代本决策。

## DEC-045 删除局域网面，Web 网关退回纯本机 IPC

- 状态：已接受
- 日期：2026-08-18
- 决策：`WebGateway` 只监听 `127.0.0.1`，只接受声明 `X-HistoryVulcan-Client: Shell` 的同机前端。
  删除设备鉴权与配对（`IDeviceAuthenticationProvider`、`IDevicePairingProvider`、
  `DeviceAuthenticationResult`、`DevicePairingResult`、`/api/pair`、`ShellServiceClient.PairAsync`）、
  令牌鉴权、绑定地址配置、CORS、按会话/按源限流，以及从未注册的 `WebCommands`
  （`vulcan.web.bind/confirm/cors/status/token` 五条命令随之消失）。
  设置键 `web.bind`、`web.token`、`web.cors`、`web.confirm`、`web.ratelimit`、`web.ratewindowlimit`
  一并退役；`web.port`、`web.portretries`、`web.frontendcatalog*` 保留。
- 证据：删除前该能力在生产代码中没有任何装配点——`WebGateway.DeviceAuthentication` 只在
  `FreezeBlockerTests` 里被赋值过；`WebCommands.RegisterAll` 全仓无调用点，运行时注册表实测
  81 条 `vulcan.*` 命令中没有 `web` 类；`ServiceHost` 的局域网确认分支读的是设置键 `lan.confirm`，
  而唯一能写确认档的 `WebCommands` 写的是 `web.confirm`，两个键从不相交，该分支在任何配置下
  都只返回 false。
- 原因：一套两年没有消费方、鉴权入口只有测试在用、确认路径因键名错配而不可达的"安全边界"，
  留着只会让每次公开面评审多背一份负担，并掩盖真实的可达攻击面。
- 代价与边界：失败鉴权不再有节流（原按远端地址限流随之删除）。在只监听回环的前提下可接受——
  能对回环发请求的人已经以当前用户身份在执行代码。**一旦将来重新对外监听，限流必须与监听
  能力同时回来**，不得只恢复监听。
- 未尽项：`WebGateway.RequestWebConfirmation` 与 `/api/confirm` 保留未删。前端
  `ShellServiceClient` 仍有 `confirmation` 的 WebSocket 处理器，但 `ServiceHost` 侧唯一的调用
  条件（源以 `Web:` 开头）已不可达，形成一条挂空的确认通道。留待网关合并（单监听器）时
  连同确认路由一起定夺，不在本次删除范围内。
- 替代条件：只有基于合并后单网关重新定义的远程访问协议可以替代本决策；不得原样复活本次删除的机制。

## DEC-043 运行模块迁入 AppData，Publish 根候选成为唯一部署面

- 状态：已接受
- 日期：2026-08-17
- 决策：独立宿主固定使用 `%AppData%\HistoryVulcan\Modules/<模块名>/`；项目库和 `z-*` 不参与
  运行发现。Vulcan 提供校验、暂存、原子替换、移除与回滚接口，安装/移除不向普通远程 MCP 暴露。
  `z-Publish/` 根部保存当前候选，`history/<发布标识>/` 保存直属完整历史包；宿主直接从
  `z-Publish/host/HistoryVulcan.exe` 运行。
- 生命周期：安装和移除先中继到前端卸载同名 UI 快照，释放模块持有的 watcher/文件句柄，再执行后台
  磁盘事务；后台确认后发布 revision 驱动前端重建。失败恢复旧包并重新发布当前 revision。
- 兼容：`IModuleDiscoverySource`、`ZModuleDiscoverySource`、`ModuleHost.ChangeDiscoveryRoots` 与
  `module.roots` 公共成员保留；独立宿主不调用它们，`vulcan.module.roots` 拒绝修改。
- 原因：运行时不应依赖项目库目录治理，候选、历史与运行副本必须分责；集中安装事务才能在文件锁、
  坏包和中途失败时提供统一回滚。
- 替代条件：只有新的、同等级的运行包存储协议能够替代本决策。

## DEC-042 按模块卸载是宿主能力，不是 Diana 特例

- 状态：已接受

- 决策：增加 `vulcan.module.unload name=`，从当前快照卸下一个已装载模块的命令、界面和
  可卸载程序集。3.12.1 起该命令服务于 `install` 释放同名快照与文件锁，不再服务试用界面。

- 后果：后台 MCP 可调用；有前端时一次调用同时卸两边。不改磁盘。卸掉 Diana 会使 MCP 工具消失，调用方自己负责。
- 替代条件：只有再次规定「安装前不得卸载同名运行快照」的同级决策可以替代。

## DEC-041 消费文档回到本仓 z 快照并入库（撤销 c9d2e90 的移除）

- 状态：已接受
- 日期：2026-08-16
- 决策：`b-Office/package/*.md` 由发布管线写入 `z-Publish/docs/`，该目录**入库**，
  并与快照其余文件一样被 `SHA256SUMS` 覆盖。跨项目读取统一走 Diana 的
  `diana.docs.catalog` → `diana.docs.vulcan`，读到的就是这份正式快照里的已发布 Markdown。
- 原因：这是一次决策回归，不是新花样。c9d2e90（3.5.0 线）把 z docs 移除，理由是
  「消费文档的单一真值由 HistoryDiana 的 `b-Office-OneHistory` 托管，快照内再放一份
  只会产生第二处会漂移的副本」。那个集中副本区**已经退役**（Diana 侧 25c1183
  「retire centralized OneHistory docs」，其 AGENTS.md 现明文写「不再建立集中模块消费文档区」）。
  前提没了，结论也就不成立：现在每个模块的消费文档就住在自己的 `z-Publish/docs/`，
  经 MCP 通道读取，本来就只有一处真值。
- 后果：修掉一个一直存在的破绽——docs 由管线生成、被**已入库的** `SHA256SUMS` 覆盖，
  目录本身却不入库，于是新克隆出来的仓库里校验清单指向一批不存在的文件，
  `Assert-ModuleSnapshot` 必然失败。入库后本仓与 `z-Publish/docs`（一直入库）一致。
  发布管线的 `Merge-PackageDocumentsIntoSnapshot` 无需改动，它本来就在写这个目录。
- 替代条件：只有再次建立集中消费文档区、并把各 `z-Publish/docs` 降级为副本的同级决策可以替代；
  在那之前不得以「避免副本」为由再次移除本目录。

## DEC-040 本项目是独立 git 仓库；项目库按一项目一仓编码

- 状态：已接受
- 日期：2026-08-14
- 决策：HistoryVulcan 的存储单位是本目录这一座 git 仓库，默认分支 `main`。
  OneHistory 项目库里每个编号项目同样各是一座仓。平行开发在仓内开分支；
  不得再把「项目」编码成共享裸仓上的一条分支或 git worktree。
  CI 与解决方案引用只认本仓文件系统；跨项目文档只读各仓 `z-Publish/docs`，运行模块只从固定
  AppData 目录发现。不得自动定位项目库，不以裸仓为哨兵，也不打开兄弟仓的 `.git`。
- 原因：旧编码里项目与分支平级，单项目多分支会与其它项目的 ref 互相污染。
  宿主本来就不治理 Git；它只需要项目库根和各项目的 Z 目录。
- 后果：`current/` 不再把本仓描述成 `2026-023-HistoryVulcan` 分支/worktree。
  DEC-023 第 3 条「门禁不得跨仓 ProjectReference」仍然有效，理由改为「邻接目录是别人的仓库」，
  不再写成「同一仓库的不同 worktree」。发布仍由 Diana 管线执行（见项目概览）。
- 替代条件：只有再次改项目库编码的同级决策可以替代。

## DEC-038 3.11.2 参数候选连续推进且必须有进展

聚焦控制台提交域、类、方法、参数名或参数值后，只要命令文本或光标实际前进，就立即重算下一层候选。
参数名因此可以进入注册的允许值/常用值，参数值可以进入下一个参数；值位于行尾时补一个空格作为下一层边界。
若位置参数结构提示的插入文本为空、文本与光标均未变化，则关闭 Popup 且不重算，阻断无限重弹。
该决策仅调整 Shell 内部补全状态机，不修改 Core、CommandBus、解析器或注册协议。

## DEC-037 3.11.1 命令助手只在控制台聚焦布局启用

控制台 Popup 命令助手只在控制台最大化/聚焦布局启用。普通停靠布局中的字母与 Tab 保持普通输入语义，
不显示 Popup、不切换命令集，也不读取或提交命令集选中项；聚焦布局继续按域 → 类 → 方法 → 参数推进。
`CommandCatalogDetail.Annotations` 作为 Shell DTO 的兼容增量传递注册注解。Core、CommandBus、解析器与命令注册协议不变。

## DEC-036 3.10.1 普通布局保留控制台补全（已由 DEC-037 取代）

3.10.1 曾规定普通停靠和最大化布局都使用 Popup。3.11.1 根据实际交互反馈收窄为只有控制台最大化/聚焦布局启用助手；
DEC-036 中“普通布局也弹 Popup”的部分不再是现行决策，首字母不得切换命令集的约束继续有效。

## DEC-035 3.5.0 semantic console focus

`vulcan.app.focusconsole` is the single stable focus-console capability shared by service, frontend, remote relay, and `--focus-console` startup. Mercury owns the global `//` registration but only dispatches this Vulcan semantic command. The old `mercury.shortcut.wakeconsole` remains a compatibility wrapper.

这里只保留仍会影响后续维护的决策。实现过程、已关闭问题和旧方案属于历史证据。

## DEC-025 3.4.0 无类直接方法回归、域聚焦与注册域权威源

- 状态：已接受
- 日期：2026-08-10
- 取代：DEC-023 第 1 条中「「无类」概念一并废止」与「所有内置指令一律三段式」两句。
  DEC-023 的其余内容（九类命名、模块域去品牌前缀、门禁解耦、无人工交互）继续有效。
- 决策：分四条同时生效。
  1. **无类直接方法正式回归，成为受控类别**。命令名允许两段 `<域>.<方法>`，
     表示「该域的直接方法」，不属于任何类。三段 `<域>.<类>.<方法>` 仍是业务指令的默认形态。
     判定规则改为纯结构式：段数为 2 即无类；段数 ≥ 3 取第二段为类；
     描述符显式声明的 `CommandClass` 永远优先。
     两段名不再回退首段作为类——`arena.cell` 从此读作「域 arena 的直接方法 cell」，
     而不是「类 arena 的方法 cell」。
  2. **注册域是绝对名解析的唯一权威源**。`CommandRegistry` 暴露已注册命令名首段的集合，
     域清单随模块装载/卸载动态变化，任何地方都不得硬编码域名字面量。
  3. **域聚焦（domain focus）**。控制台输入可聚焦到某个域；聚焦期间：
     - 输入首段命中**已注册域**时按绝对名解析，不拼前缀；
     - 否则自动补上当前聚焦域前缀。
     因此 `mercury.go`、`vulcan.*` 等在任意聚焦状态下都能直接输入，
     无需每个域各自提供一条退出指令。聚焦状态与控制台域筛选下拉双向同步，
     下拉选「全部」即退出聚焦。
  4. **补全按域 → 类 → 方法 → 参数分段推进**，不再一次性平铺全名候选。
     参数候选只能来自模块注册时提供的 `ParameterSpec`，宿主与 Mercury 都不得猜测参数名。
- 原因：
  1. 上一轮把无类一并废止是矫枉过正。域的直接方法是一个真实且长期需要的类别——
     它给「插一条快捷方法」留出位置，而不必为一两条命令硬造一个类。
     受控地保留它，比让每个模块各自发明变通更可控。
  2. 绝对名脱固若依赖硬编码域清单，每接入一个新模块都要改宿主，
     这正是 DEC-023 第 3 条要消除的那种跨仓库耦合。
  3. 退出域聚焦如果做成每个域一条退出指令，会让每个模块都被迫耦合一份与自身业务无关的命令；
     用「首段是已注册域就按绝对名解析」这一条规则，退出能力自然涌现，零新增指令、零域耦合。
- 后果：
  - **影响面**：仍在注册两段式指令的消费方，其命令从「类.方法」改判为「域的直接方法」，
    在命令集与控制台里改为「无类」分组显示。命令名与调用方式不变，只是归类显示改变；
    其首段同时成为已注册域，参与绝对名解析。
    OneHistory 体系内已无此类消费方，本条只对体系外的独立分支适用。
  - 命令集与控制台恢复「无类」筛选项；DEC-023 删除的 `NoneLabel` 以受控形式回归，
    但只作为显示标签，不再承担类推导逻辑。
  - `mercury.go` 是无类直接方法的第一个正式用例：`mercury.go <域>` 进入聚焦，
    `mercury.go` 无参退出。
- 替代条件：若某个域的直接方法超过 5 条，应重新评估是否该为它们建类。

## DEC-024 3.3.2 诊断指令退出正式命令集，测试套件按执行效率与功能内聚重整

- 状态：已接受
- 日期：2026-08-10
- 决策：分两部分。
  1. **诊断指令不属于正式命令集**。承压注水 `vulcan.log.flood`（3.3.1 的 `debug.logflood`）
     三重收口：宿主默认**不注册**，需显式设置 `diagnostics.commands=true`；描述符标记
     `Dangerous` 并带确认提示；`McpExposurePolicy` 按名硬排除，MCP/Web 永不可达。
     保留能力而非删除——它是技术合同验收 8 / N-03 的承压入口，也是异步长任务 + Progress 的示范。
  2. **测试套件以执行效率为首要目标，按功能内聚组织**。不以拆分热点类为目的：
     - 「推进 UI」收敛为唯一所有者 `UiTestHost`（`Pump` / `PumpUntil` / `PumpFor` + `RunSta`），
       替换散落在三个文件里的三份拷贝；
     - 测试集合按**争用的独占资源**分组（`ui-foreground`、`network-gateway`），组内串行、组间并行，
       取代程序集级的一刀切串行开关；
     - UI 用例有 60 秒硬上限，超时抛出具名 `TimeoutException`。
- 原因：
  1. 影子域 `debug` 退役后，原先按 `"debug."` 前缀生效的 MCP 硬排除失配，承压注水一度可被远程
     触发（`rate=100000 × seconds=600` 即 6000 万条日志），这是对自身的拒绝服务面。
     且它本就不该出现在最终用户的命令集里。
  2. `PumpDispatcher` 无条件固定睡 300ms，43 个默认调用点占掉整轮约三分之二墙钟时间；
     `RunSta` 裸 `Join()` 使任何阻塞变成整轮静默挂死（曾出现 25 分钟零输出、
     testhost 累计 CPU 仅 9.5 秒），CI 上表现为 job 超时被杀且日志无线索。
- 后果：
  - 命令集不再出现 `debug` 类；需要承压时由宿主显式开启诊断开关。
  - 全量测试从 42 秒降到约 25 秒，用例数不减（159）。`DockingContractTests` 5.9 秒 → 1.1 秒。
  - 盲等被替换为具名等待：`PumpUntil` 表达「在等什么」，`PumpFor` 仅用于被测对象真的依赖时间
    （控制台 100ms 批量合并、`DockingHost` 200ms 缩放去抖）。这些时间常量此前被 300ms 盲等掩盖。
  - 剩余耗时的两个大头是结构性的，本轮不动：`ShellChromeContractTests` 每个用例构造完整
    `ShellWindow`（14.4 秒 / 33 用例）；`RemoteConfirmationQueueTimesOutWithoutExecutingOrDuplicatingAudit`
    受 `McpGateway` 确认超时下限 `Math.Clamp(t, 10, 600)` 约束固定耗时 10 秒——
    缩短它需要放宽一个安全相关的下限，不做。
- 替代条件：诊断指令若要进入正式命令集，需同级决策并重新评估远程暴露面；
  测试分组若要改为共享 `ShellWindow` 夹具，必须先证明用例间不存在状态污染。
