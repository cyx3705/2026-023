## DEC-070 5.9.0 统一模块契约第一段：事件、运行环境、目录指令、测试装载

- 状态：已接受；日期：2026-09-30；关联：REQ-HOST-080…083。来源：用户指出「改宿主要关心每一个模块，而不是统一契约」，
  批准 `b-Office/history/6.0.0-统一模块契约设计稿.md` 全部条款并按稿中建议拍板。
- **契约只有一条总线和一个上下文**：7/9 模块本来只用「登记指令 + 执行指令」；代价来自 Aurora、Portunus 直接用总线内部，
  4 个模块引用实现程序集 Services，以及数据目录、运行方式、宿主位置没有契约只好各自猜。5.9.0 把缺的都补成契约，6.0.0 再收口。
- **只增不删**：新成员都带默认实现，`CommandBus` / `CommandRegistry` 实现新窄接口 `ICommandBus` / `ICommandRegistrar`，
  `IModuleContext.Bus` 仍给具体类。现有模块二进制不改即可装载；公开 API 基线相对 5.8.0 只有新增。
- **事件用通用具名主题**（拍板 2）：模块也能发自己域下的主题，宿主不必每加一种事件就改契约；载荷只按 JSON 约定。
  每个订阅串行投递以保证日志顺序；`vulcan.command.executed` 不带指令全文，因为参数里可能有密钥。
- **数据目录放在包槽位之外**（拍板 1、4，偏离设计稿 C6「就是 `槽/data`」）：卸载会删整个槽位，只保留 `data/` 会留下被发现流程当作坏包的残槽。
  改为 `%AppData%\HistoryVulcan\ModuleData\<模块名>`，卸载默认保留，`purge=true` 才删。旧的 `槽/data` 保留逻辑维持到 6.0.0；
  旧数据由各模块迁移时自己搬，宿主不替模块搬内容。
- **确认要不要，而不是确认文案**：`ConfirmPrompt` 是按参数生成的委托，目录行只给 `RequiresConfirmation`（偏离设计稿 C7 的 `confirmPrompt`）。
- **来源盖章推迟到 6.0.0**：`Bus` 还是共享的具体对象，没法按模块包一层；5.9.0 先让 `module:` 前缀可信，`diana.` 兼容到 6.0.0。
- **测试装载走命令行**：`--probe` 复用正式组合根，只把运行区与数据根换成临时目录；模块测试不再编译依赖 `ModuleHost`。
- 新增 `vulcan.host.info` 进命令行白名单（此前名单只有开发管线与恢复两组；这条是只读自报，脚本与模块测试替代按固定路径猜宿主）。
- 走次版本 5.9.0（新增公开面），冻结线保持 v5.4.0。模块不必跟版。

## DEC-069 5.8.0 宿主不登记模块；命令行回执去重

- 状态：已接受；日期：2026-09-30；关联：REQ-HOST-078、REQ-HOST-079。来源：用户要求「改模块、新建模块必须不用碰宿主代码，
  宿主是冻结的而不是随模块增长的」，并要求检查开发管线 CLI 返回内容是否过多。
- **登记表搬回模块仓**：`b-Code-Eng/pipeline/module-publish.manifest.json` 删除。每个模块的发布描述（版本源、清单、
  打包项目与文件、验证步骤）只有模块自己知道，也只随模块代码变化；放在宿主仓意味着每新建一个模块、每加一条验证
  都要改宿主仓，且 `vulcan.dev.start` 开得出工作区、`submit` 却因「没登记」拒收（Apollo、Strenua 都踩过）。
  现在写在模块仓 `project.manifest.json` 的 `publish` 节——这份文件本来就是项目给工具读的自述，模块名直接取 `project.name`，
  不另设一个名字。**不用单独文件**：少一个要同步的地方，模板派生时一并改名。
- **描述跟着工作区走**：submit / finish 读工作区里的描述，本轮加了验证步骤就在本轮生效；工作区没有这一节（5.8.0 前开出的）
  才退回主树，老工作区不必重开。
- **宿主只认识自己**：`IsHostProject` 不再去登记表查 `kind=host`，宿主身份就是两个常量。冻结标签期望值仍放在宿主仓
  （`host-freeze.json`），理由与原来相同：期望值不能与被守护的 `project.manifest.json` 同处一文件。
- **发现不是登记**：`vulcan.release.modules` 与 `name=` 兜底定位改为现场扫描项目库根，结果不落盘。
- **回执去重**：5.7.0 的 DEC-067 把「文字 + JSON」的重复记为 CLI 通用格式、不在管线里特判；本次就在 CLI 通用层去掉——
  命令行面上 20 条指令全是宿主自己的，逐条核对过正文已覆盖 Data（唯一例外 `vulcan.command.show` 的参数，已补进正文）。
  `--runtime` 会执行任意模块指令，模块的正文不保证覆盖 Data，那一条路径不动。管线回执另做三处收敛：脏文件清单改摘要、
  submit 成功段的三条重复指引合成一条、失败回执直接带原因。
- **迁移**：9 个模块仓各自在 `project.manifest.json` 补 `publish` 节（内容逐字取自原登记表），模板 `0000-002-ModuleReady`
  改为派生时直接带 `publish`。5.7.1 未单独发版，并入本版。
- 只动内部实现，公开 API 零变化（5.8.0 基线与 5.7.0 逐字相同）；因管线的输入约定变了（模块须自带描述）走次版本。
  冻结线保持 v5.4.0，模块二进制不必跟版。

## DEC-067 5.7.0 开发管线按使用反馈收敛参数与回执

- 状态：已接受；日期：2026-09-21；关联：REQ-HOST-072…076。
- 来源：HistoryMinerva 4.12.0 一轮完整 start → submit → finish 的实际使用，意见稿见
  [5.7.0 开发管线易用性升级说明](../history/5.7.0-开发管线易用性升级说明.md)。
- **能推出来的就不让人填**：模块由工作区项目反查，提交说明取 slug。`name=` 保留，但只作校验——
  写错时拒绝并给出两个值，不替人选。
- **dev.submit 不再要 allowDirty**：工作区从干净 HEAD 开出，未提交改动就是 submit 要提交的东西；
  每次都得传的授权不是授权。主树 `release.cycle` 的门保留，那里的脏改动才可能是别人的。
- **finish 的 msg 不再有意义**：快进合并不产生提交。为不打断旧调用，接受并提示已忽略，而不是报「未知参数」。
- **「已热重载」必须证明接上了**：曾出现回执成功、模块 attached=false 的情况。核对放进 `InstallAsync`，
  submit 与 finish 两条热装路径一起受益；问不到时照实写「未核对」。
- **不做的**：三条指令的 `help` 参数没有做——缺参时总线已回「用法: …」，`vulcan.command.help` 也能查，
  再加一个开关要改参数校验层，收益不抵。回执「文字 + JSON」的重复属于 CLI 通用格式，不在管线里特判。
- 只动内部实现，公开 API 零变化，走次版本 5.7.0（CLI 参数语义有变化），冻结线保持 v5.4.0。模块不必跟版。

## DEC-066 5.6.1 git 输出设置补在进程层，不在某一个调用点

- 状态：已接受；日期：2026-09-19；关联：REQ-HOST-071。
- 起因是 Janus 5.10.0 修同一个毛病时，在 `vulcan.dev.submit` 的回执里看见宿主自己也在打八进制。

  因此单开一条测试钉住「非 git 不受影响」。

  模块不必跟版。

## DEC-065 5.6.0 大段结果降到 Debug，控制台在 Info 档位上是一张菜单

2026-09-19：用户要求先查清「级别是模块声明的还是宿主定的」，再据此决定改哪一层；核对后是宿主定的，
遂授权改宿主。

核对依据是三天真机日志（shell-20260917～19）按类别与命令名的统计：Info 级的量几乎全部来自
`cmd:result:*`。`vulcan.command.list` 一项三天 8.2 MB / 6.7 万行；各模块 `*.ui.data`、`*.ui.describe`、
`*.ui.actions` 约 2 MB，其中 janus 单条最大 38 KB、juno 与 aurora 53 KB、cet4 49 KB，都是**一行** JSON。
这些是页面取数的机器面载荷，人不读、消费方也不从控制台读。

- 级别不可能由模块声明：`CommandResult` 只有 Success / Message / Data，`Progress<string>` 也只有一行文本；
  `result.Success ? Info : Error` 从第一版起就写死在 CommandBus 里。因此没有「反向扫出超长消息、
  让模块把自己那条注册成 Debug」这条路可走，规则只能长在总线上。
- 也不采用按域或命令名列白名单：今天列全了，下一个模块的 `*.ui.data` 照样刷屏。改按消息形状判。
- 大段结果在 Info 上留一行提要而不是整条消失：控制台的每一行要仍然答得出「这条指令做完了没有」。
- 失败不降级。要消灭的是看不见人要读的那几行，不是看不见出了什么错。

已知代价（明确接受）：人手敲 `vulcan.command.list` 时，Info 档位上只剩「✓ 命令集: 249 / 249 条（另有 249 行…）」，
整张表要切到 Debug 或去命令集页面看。纯增量行为变化，走次版本 5.6.0，冻结线保持 v5.4.0；公开 API 一个字没动，
模块不必跟版。

行为见技术合同 REQ-HOST-005。

## DEC-064 5.5.0 宿主日志是唯一的控制台日志

2026-09-14：用户选定「改宿主 + Aurora」（而非只让 Aurora 读日志文件），并定下原则：以后所有命令执行的日志，不论哪个模块，
全部走控制台；控制台不在前端另跑一份输出。授权宿主发版部署。

起因：HistoryApollo 0.3.0 把每轮模型调用写进 `CommandContext.Progress`，服务端 `shell-*.log` 里完整记着，Aurora 控制台却一行不见。
核对后是结构性缺口：Aurora 界面总线经 RemoteExecutor 把命令交给宿主总线，只拿回最终回执；宿主总线的回显与进度只写宿主 ShellLog，
控制台却只订阅 Aurora 自建的 MemoryShellLog，宿主又不向模块公开日志。经宿主执行的所有指令（含 Minerva 自己的进度行）都受影响，并非 Apollo 引入。

- `IModuleContext` 新增带默认实现的 `Log`，宿主上下文返回宿主总线的那一个 IShellLog。Aurora 的控制台与界面日志改用它，不再自建第二份。
- CommandBus 把命令交给 RemoteExecutor 时本地不再回显与记结果：共用一份日志后两边各记一遍就是重复，且本地注册表不认识远端命令、无法脱敏。
- 纯增量公开 API 加一处行为收紧，走次版本 5.5.0，冻结线保持 v5.4.0。旧 Aurora 1.22.x 在 5.5.0 宿主上照常接入，只是界面发往宿主的命令在它自己的控制台里不再有回显，须与 Aurora 1.23.0 同批部署。
- 不采用「宿主把日志转交前端、前端再抄一份」：那仍是两份日志。也不采用读日志文件：绑死路径、格式与轮转。

行为见技术合同 REQ-HOST-004。

## DEC-063 5.4.0 总线前端单一所有权与宿主内部面收回

2026-09-14：用户明确指定 5.4 并授权跨模块一次改到位。这是常规需走主版本的兼容变化的例外，不作为后续删除先例。

- ServiceHost 全部类型，Services 的 AppPaths、SettingsService、ShellLog、开发管线入口、OfflineModuleInstall、命令目录注册入口，以及 Core 的 CommandHistory、CommandSelectionState、IDeferredStartupWork、CliExposurePolicy 收回 internal 或删除。ModuleHost 只保留模块 Smoke 需要的装载器面。
- 同轮在模块工作区迁移 Aurora、Janus、Minerva 的消费代码。

精确变更保存在 5.4.0 PreFreeze 基线，消费摘要见[模块 API](../package/模块API.md)。此次授权不含提交、标签、推送、正式发布和重启宿主部署。
